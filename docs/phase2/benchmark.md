# Phase 2 성능 측정 — 인덱스 조회 vs 선형 탐색 (P2-04)

100만 건을 Phase 1 SQL 처리기로 넣은 뒤, `WHERE id`(B+ 트리 인덱스)와 `WHERE age`(선형 탐색)의 조회 시간을 비교한다.
재현: `make bench`(Windows는 `mingw32-make bench`). 표는 `tools/bench.py`의 출력을 그대로 옮긴 것이다(2026-11-16 측정).

## 결론

| | id 조회 (INDEX LOOKUP) | age 조회 (FULL SCAN) | 차이 |
|---|---:|---:|---:|
| 조회 한 번 (시작 비용 제외, 중앙값) | **0.02 ms** (가운데 id) | **700~840 ms** | 약 3만~4만 배 |
| 프로세스 전체 (시작 918 ms 포함) | 약 918 ms | 약 1,620~1,760 ms | 약 1.8~1.9배 |

- 인덱스 조회는 100만 건에서도 노드 4개(높이 4)를 거쳐 한 줄만 읽으므로 0.01~0.04 ms다. 선형 탐색은 2천만 바이트를 모두 읽고 파싱해 0.6~0.9초가 걸린다.
- **CLI 한 번 실행 전체로 보면 차이가 2배 미만이다.** 시작할 때 `table_open`이 파일 전체를 읽어 검증하고 인덱스를 다시 만들기 때문이다(917.5 ms, 선형 탐색 한 번과 같은 규모). 메모리 인덱스의 이득은 한 번 띄운 프로세스가 조회를 여러 번 받을 때 드러난다(Phase 3 서버 구조의 동기).
- 없는 id는 트리에서 바로 끝나 파일을 읽지 않는다(0.0002 ms).

| 항목 | 값 |
|---|---|
| SQL 생성 (Python) | 1.1 s |

## 조회 시간 (시작 비용 제외)

| 조회 | WHERE | 계획 (EXPLAIN) | 결과 행 | 중앙값 ms | 최소 ms | 최대 ms |
|---|---|---|---:|---:|---:|---:|
| id 단건 — 처음 | `id = 1` | INDEX LOOKUP | 1 | 0.0409 | 0.0281 | 0.1158 |
| id 단건 — 가운데 | `id = 500000` | INDEX LOOKUP | 1 | 0.0197 | 0.0172 | 0.1075 |
| id 단건 — 끝 | `id = 1000000` | INDEX LOOKUP | 1 | 0.0112 | 0.0071 | 0.1199 |
| id 단건 — 없음 | `id = 1000001` | INDEX LOOKUP | 0 | 0.0002 | 0.0002 | 0.0012 |
| id 범위 1,000건 | `id BETWEEN 500000 AND 500999` | INDEX RANGE SCAN | 1,000 | 1.765 | 1.270 | 3.184 |
| age 단건 — 일치 많음 | `age = 30` | FULL SCAN | 6,623 | 838.8 | 588.1 | 941.6 |
| age 단건 — 일치 없음 | `age = 151` | FULL SCAN | 0 | 699.6 | 582.8 | 891.8 |

"계획" 열은 같은 조건의 EXPLAIN 출력(계획 시점 통계)이고, 나머지 열이 `--timing`의 실제 실행 측정값이다.

## 읽는 법과 주의

- **id 처음(0.04 ms)이 끝(0.01 ms)보다 느린 이유:** 조회 묶음에서 첫 번째로 실행되는 문장이라 캐시·첫 `fseek` 같은 처음 한 번의 비용을 함께 낸다. 트리 탐색 자체는 어느 id든 노드 4개로 같다. 0.01~0.04 ms 차이는 이 규모의 측정 잡음 범위다.
- **범위 1,000건 1.8 ms:** 시작 리프를 한 번 찾은 뒤 리프 연결을 따라가며, 파일에서는 첫 줄로만 이동하고 이어 읽는다. 건당 약 1.8 µs(읽기·파싱·출력 포함)로, 같은 1,000줄을 선형 탐색이 지나가는 비용(약 0.7 µs/줄)에 출력 비용이 더해진 수준이다. 범위가 작을수록 선형 탐색 대비 이득이 크다.
- **age 두 조회의 중앙값 차이(840 vs 700 ms):** 출력 6,623행의 비용도 있지만, 최소값은 588 vs 583 ms로 거의 같다. Windows 데스크톱에서의 프로세스 간 변동이 커서 중앙값보다 최소값이 순수 탐색 비용에 가깝다.
- **INSERT 건당 43.6 µs:** INSERT마다 `fflush`로 파일에 확정하므로(실패한 INSERT가 남지 않는 Phase 1 규칙) 건마다 시스템 호출이 든다. 측정 대상(조회)과는 별개다.
- 결과 출력은 일반 파일로 버렸다. Windows의 `NUL`로 보내면 C 런타임이 줄마다 바로 써서 출력 비용이 몇 배로 부풀려진다(spec "측정 계약").
- 시간 측정은 단조 시계(Windows `QueryPerformanceCounter`) 기준이다. 0.0002 ms 같은 값은 시계 해상도(약 0.1 µs)에 가깝다.

## 인덱스 메모리 — 예상과 실측

| | design.md 예상 | 실측 |
|---|---|---|
| 리프 | 약 31,000개 | 31,250개 (= 1,000,000 / 32) |
| 내부 노드 | — | 976개 |
| 높이 | — | 4 |
| 메모리 | 약 33 MB | 32.7 MB (트리가 요청한 바이트, malloc 오버헤드 제외) |

리프가 정확히 1,000,000 / 32개인 것은 예상대로 **모든 리프가 절반(32개)만 찬 상태**라는 뜻이다. id가 항상 오른쪽 끝에 들어오는데 분할은 반으로 나누므로, 왼쪽 리프는 다시 채워지지 않는다.

**개선 여지(이번에는 하지 않음, DB-P2-D12):** 오른쪽 끝 리프가 넘칠 때 꽉 찬 채로 두고 새 키만 새 리프로 보내면(순차 삽입 최적화) 리프 수와 메모리가 거의 절반(약 16 MB)으로 준다. 높이는 이 규모에서 그대로 4로 예상된다. 트리 모양이 바뀌어 분할 모양 테스트와 `bpt_demo` 학습 출력이 달라지므로 범위 밖으로 두었다.
