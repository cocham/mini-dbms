# Phase 2 탑다운 학습 가이드

결과물 → 전체 지도 → 최소 기능 실습 → 필요한 이론 순서로 읽는다. 기능 하나가 끝날 때마다 이 문서에 실습이 추가된다.
설계 근거는 [design.md](design.md), 코드 따라가기는 [implementation.md](implementation.md)에 있다.

## 1단계 — 왜, 무엇을 (Why & What)

**문제:** Phase 1은 `WHERE id = 3`도 파일을 처음부터 끝까지 읽는다. 100만 건이면 한 명을 찾으려고 100만 줄을 읽는다.

**해결:** 책 뒤의 "찾아보기"처럼 id → 그 레코드가 파일 몇 번째 바이트에 있는지를 정리해 둔다. 그 목록을 빠르게 찾을 수 있게 정렬된 균형 트리(B+ 트리)로 만든다.

**끝나면 할 수 있는 것** ([spec.md](spec.md) "최종 결과"):

- 100만 건을 Phase 1 SQL 처리기로 넣고
- `WHERE id = ?`(인덱스)와 `WHERE age = ?`(선형 탐색)의 시간 차이를 숫자로 보여 주고
- `EXPLAIN`으로 어떤 경로를 탔는지, `BETWEEN`으로 리프 연결을 어떻게 쓰는지 설명할 수 있다.

## 2단계 — 전체 지도 (Big Picture)

구성 요소는 넷이다.

| 요소 | 역할 | 비유 (실제 동작과 다른 점) |
|---|---|---|
| users.tsv | 진짜 데이터. 디스크에 남는다 | 책 본문 |
| B+ 트리 | id → 바이트 위치. 메모리에만 있다 | 찾아보기. 단, 매번 책을 처음부터 훑어 새로 만든다 |
| Storage | 파일과 트리를 함께 관리 | 사서 |
| Executor | 조건을 보고 "찾아보기를 쓸지, 본문을 다 읽을지" 결정 | 질문을 받는 창구 |

```text
            ┌──────── 시작할 때 한 번: 파일 전체를 읽어 트리를 만든다 ────────┐
            ▼                                                               │
SQL → Parser → Executor ──WHERE id──▶ B+ 트리 ──위치──▶ fseek ──▶ users.tsv ┘
                     └───WHERE age──────────────────────▶ 처음부터 끝까지 ──▶ users.tsv
```

### 확인 질문

위 그림만 보고 자기 말로 답한다. 코드·문서는 보지 않는다. 두 질문에 답하고 검토를 받은 뒤 3단계로 간다.

**질문 1.** 프로그램을 종료했다가 다시 실행하면 B+ 트리는 어떻게 될까? 그래도 `WHERE id = 3`을 제대로 찾을 수 있는 이유는?

> 내 답: 트리는 처음부터 다시 생성된다. id가 트리에 인덱스로 저장되어 있으므로 해당 노드를 찾아서 바이트 값으로 바로 해당 파일 위치로 가서 레코드를 가져온다.

검토(대체로 맞음): 빠진 것은 "무엇으로 다시 만드나". 디스크에 남은 users.tsv를 `table_open`이 처음부터 읽으며 줄마다 (id, 줄 시작 바이트)를 다시 계산해 넣는다. **파일이 원본, 트리는 파일에서 언제든 다시 만들 수 있는 사본**이라 재실행해도 정확하다.

**질문 2.** `INSERT`를 한 건 실행하면 `users.tsv`와 B+ 트리 중 어느 쪽이 먼저 바뀔까? 순서를 그렇게 정한 이유는?

> 내 답: B+ 트리가 먼저 변경된다. 해당 id의 데이터가 어디 있는지 알아야 거기서부터 데이터를 저장할 수 있기 때문이다.

검토(반대): **파일이 먼저, 트리가 나중.** 저장 위치는 항상 파일 끝(append)이라 트리에 물을 필요가 없다. 트리는 위치를 정하는 쪽이 아니라 저장된 위치를 적어 두는 쪽이다(`ftell`로 끝 위치 → 기록 → 성공 후 `bpt_insert`).
순서의 이유: 트리 → 파일 순서에서 사이에 실패하면 트리가 없는 줄을 가리킨다. 파일 → 트리 순서에서 실패하면 이번 실행에서만 조회가 안 되고, 다음 실행에서 파일로 트리를 다시 만들면 복구된다. 원본을 먼저 확정하고 사본을 나중에 갱신한다.

**질문 2 보충.** `bpt_insert`를 파일 기록 앞으로 옮겼는데 `fprintf`가 디스크 가득 참으로 실패했다면 (a) 같은 실행에서 그 id 조회는? (b) 재실행 후 같은 조회는?

> 내 답: insert에 실패했으므로 조회 오류가 남. 둘 다 오류 아닌가

검토((a) 맞음, (b) 틀림): (a)는 트리가 없는 줄을 가리켜 "인덱스와 데이터 파일이 일치하지 않습니다" 오류(읽은 줄의 id 재확인 덕분에 엉뚱한 행 대신 오류). (b)는 재시작 때 파일로 트리를 다시 만들므로 id가 트리에 없음 → **오류가 아니라 헤더만 출력(결과 없음)**. 어긋난 쪽이 메모리 사본이라 재시작이 자동으로 다시 맞춘다. 실제 코드(파일 → 트리)라면 (a)도 결과 없음. CLI는 fail-fast라 (a)까지 가지 않지만 Phase 3 서버에서는 실제로 일어난다. 줄 일부만 쓰였다면 재시작 시 "마지막 줄이 LF로 끝나지 않음" 손상 오류(원자적 복구 미보장).

## 3단계 — P2-01: id 조회 최소 경로 (Quick Win)

진행 방식(2026-11-15 변경): 2단계 확인 질문에 답한 뒤, P2-01 코드를 한 겹씩 내려간다.
Executor 경로 분기 → `table_find_by_id` → `bpt_search` → `bpt_insert`와 분할. 겹마다 질문 하나와 예측 하나를 하고 멈춘다.
아래 미션은 코드를 읽어 가면서 해당 겹에서 함께 한다.

### 실행

```text
make
mkdir -p data          # data/는 Git에서 제외된 실행 데이터 폴더. --data-dir은 마지막 한 단계만 만들어 준다
build/minidb --data-dir data/p2 examples/phase2_id_lookup.sql
```

기대 출력:

```text
INSERT 1        (×5)
id	name	age
3	O'Brien	25        ← WHERE id = 3   : 인덱스 조회
id	name	age         ← WHERE id = 99  : 트리에 없음, 파일을 읽지 않음
id	name	age
1	민수	25          ← WHERE age = 25 : 선형 탐색
3	O'Brien	25
```

같은 명령을 한 번 더 실행하면 6~10번이 추가된다. `rm -rf data/p2`로 처음 상태로 돌린다.

### 미션 A — 바이트 위치 예측

`data/p2/users.tsv`를 처음 상태로 만들고 예제를 한 번 실행한 뒤, **id 4가 저장된 줄의 시작 위치(바이트)**를 계산해 본다.
힌트: 한글은 UTF-8에서 한 글자 3바이트, 탭과 LF는 1바이트, 첫 줄은 위치 0에서 시작한다.

확인 방법(위치 + 1을 넣는다):

```text
tail -c +$((예측값 + 1)) data/p2/users.tsv | head -1
```

예측이 맞으면 `4	현우	40`이 줄 처음부터 정확히 나온다. 틀리면 줄 중간부터 잘려 나온다. 이 위치가 `table_find_by_id`가 `fseek`할 값이다.

### 미션 B — 트리 모양 예측

`bpt_demo`는 SQL 없이 트리만 보여 준다. 실행 **전에** 높이를 종이에 적고 비교한다.

| 명령 | 예측: 높이 | 예측: 루트의 키 |
|---|---|---|
| `build/bpt_demo 3 2` | | |
| `build/bpt_demo 3 3` | | |
| `build/bpt_demo 3 7 4` | | |
| `build/bpt_demo 4 7 4` | | |

이어서: 차수 3에서 키를 1개씩 늘려 가며 **높이가 4가 되는 첫 개수**를 예측하고 확인한다. `--shuffle`을 붙여 같은 개수를 섞어서 넣으면 리프 모양이 어떻게 달라지는지도 본다.

### 미션 C — 코드 한 줄 바꾸고 결과 예측

[storage.c](../../src/storage.c)의 `table_append`에서 `bpt_insert(t->index, id, ...)`를 부르는 `if` 블록 전체를 주석 처리하고 `make`한다(INSERT가 트리에 등록되지 않게 된다).

실행 전에 예측한다:

1. `rm -rf data/p2` 후 예제를 실행하면 `WHERE id = 3`의 결과는?
2. 이어서 `SELECT * FROM users WHERE id = 3;` 한 줄짜리 SQL 파일을 **새로 실행**하면?
3. `make test`에서 실패하는 테스트는 어떤 종류일까? (같은 실행 안 / 재시작 후)

확인 후 주석을 되돌리고 `make test`가 다시 전부 통과하는지 본다.

[storage.c](../../src/storage.c)의 `table_open`에서 `bpt_create(BPT_DEFAULT_ORDER)`를 `bpt_create(3)`으로 바꾸면 `make test` 결과가 달라질지 예측하고 확인한다. 확인 후 되돌린다.

## 4단계 — 이론은 질문이 나올 때 (Just-In-Time)

이론은 미리 적어 두지 않는다. 실습이나 코드 읽기 중에 생긴 질문을 다룬 뒤, 그 내용만 여기에 기록한다.

| 날짜 | 질문 | 정리 |
|---|---|---|
| 2026-11-15 | Phase 2에서 ID 자동 생성 방식이 바뀌었나? | 아니다. `table_open`이 복원한 `last_id` + 1을 그대로 쓰고, 기록 뒤 `bpt_insert(id, 위치)`로 트리에 등록하는 단계만 추가됐다. 트리의 가장 오른쪽 키로도 최대 id를 알 수 있지만 `last_id`로 충분해서 쓰지 않는다 |
| 2026-11-15 | `last_id`는 프로그램이 끝나면 사라지는 지역변수 아닌가? | 지역변수가 아니라 힙에 만든 `Table`의 필드라 `table_close`까지 살아 있다(한 실행 동안 INSERT마다 이어짐). 프로세스가 끝나면 사라지는 것은 맞고, 다음 실행의 `table_open`이 파일 마지막 줄의 id로 다시 계산한다 |
| 2026-11-15 | 시작할 때마다 전체를 읽는 건 비효율적인데, 인덱스가 생기면 최적화할 수 있지 않나? | 메모리 인덱스는 그 전체 읽기에서 만들어지므로 읽기를 대신할 수 없다(`last_id`는 같은 읽기의 덤). 인덱스를 디스크에 저장하면 가장 오른쪽 리프로 최대 id를 O(log N)에 얻을 수 있지만 "메모리 기반" 조건과 파일 간 일관성 문제가 생긴다. 이 과제에서의 해법은 Phase 3 서버처럼 프로세스를 계속 띄워 시작 비용을 한 번만 내는 것. 실제 비용은 P2-04에서 측정 |
| 2026-11-15 | 중간 삽입도 가능하지 않나? 항상 파일 끝에 저장된다는 보장이 있나? | 보장된다. ① 쓰기는 INSERT뿐이고 id는 항상 `last_id + 1`(사용자 지정 금지)이라 새 id가 늘 최대 ② `fopen(..., "a+b")`의 append 모드는 fseek 위치와 상관없이 모든 쓰기를 파일 끝으로 보낸다(C 표준) ③ `table_open`이 id 증가 순서를 검증. 파일 중간에 끼우면 뒤의 모든 줄이 밀려 트리의 바이트 위치가 전부 틀어지므로, 실제 DBMS도 데이터 파일 위치는 고정하고 정렬은 인덱스가 맡는다. 중간 삽입은 파일이 아니라 B+ 트리에서 일어난다(`bpt_demo --shuffle`) |
| 2026-11-15 | 저장 방식은 B+ 트리 개념과 깊지 않으니 내 방식대로 해도 되나? | 된다(과제도 포맷 자유). 트리는 id → "주소" 정수만 알고 파일을 모르므로 바꿀 곳은 storage.c뿐. 단 저장 방식이 지킬 조건: ① 주소로 레코드 하나를 바로 읽을 수 있음 ② 주소가 바뀌지 않음(바뀌면 인덱스도 갱신) ③ 저장 시점에 주소를 앎 ④ 메모리 인덱스라면 파일을 훑으며 주소를 다시 계산할 수 있음. 형식에 따라 리프 값의 의미만 달라진다(바이트 위치 / 레코드 번호 / 페이지+슬롯) |
| 2026-11-15 | 디스크 저장에 실패했으면 어차피 데이터가 없는 것 아닌가? | 맞다. 그래서 올바른 답은 "결과 없음"이고 (b)가 정상이다. (a)의 문제는 데이터가 없는데 인덱스가 "있다(위치 61)"고 주장하는 내부 모순. 다음 INSERT가 같은 위치 61에 기록되면 트리가 다른 사람의 줄을 가리키게 되는데, 읽은 줄 id 재확인이 이를 막는 안전장치이고 근본 해결은 파일에 확정된 것만 트리에 적는 파일 → 트리 순서 |
