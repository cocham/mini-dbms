# Phase 5 확인·측정 — 100만 행에서 커서 페이지 조회

DB-P5-D10에 따라 **변경 없는 100만 행**에서 세 가지를 확인했다.

1. 전체 조회가 실패하는가
2. 페이지 전체 순회가 정확한가
3. 페이지 응답 시간과 바이트

부하 측정(동시 클라이언트, 처리량)은 하지 않았다.

## 환경과 방법

| 항목 | 값 |
|---|---|
| 실행 | Docker Desktop 28.5.1(WSL2, 커널 6.18.58.1), 이미지 `gcc:13`(GCC 13.5.0), 컨테이너에서 보이는 CPU 8개 |
| 데이터 | `id TAB userNNNNNN TAB id%151` 100만 행(약 20 MB). `tools/load.py`와 같은 형식이다. 컨테이너 안 `/tmp`에 둔다(Windows 공유 폴더를 피함, Phase 3 benchmark "측정 중 발견한 환경 병목") |
| 서버 | 기본 설정: 워커 4개, 응답 상한 8 MiB·100,000행 → 페이지 상한 1000행(기본 limit 100) |
| 도구 | `tools/page_bench.py`(`make page-bench`). 요청마다 새 연결을 맺고, 연결 → 요청 보내기 → 응답 끝까지 받기를 파이썬에서 잰다 |
| 반복 | 전체 조회 5회, 페이지마다 30회. 측정 전에 선형 탐색 한 번으로 파일을 페이지 캐시에 올린다 |

**읽을 때 주의:**
- 응답 시간에는 파이썬 처리와 TCP 연결 비용이 들어 있다. 서버 내부 처리 시간보다 크다.
- 클라이언트와 서버가 같은 컨테이너에서 CPU를 나눠 쓴다. 숫자는 이 환경에서의 비교로만 읽는다.
- 실제 네트워크를 거치지 않는다(127.0.0.1).

## 결과 (2026-11-18, 두 번 실행)

### 1. 전체 조회 `SELECT * FROM users;`

| 실행 | 상태 | 코드 | 응답 바이트 | 응답 시간 중앙값(5회) | 메시지 |
|---|---|---|---|---|---|
| 1 | 400 | `RESULT_TOO_LARGE` | 146 | 36.3 ms | 결과가 너무 많습니다 (요청당 최대 100000행) |
| 2 | 400 | `RESULT_TOO_LARGE` | 146 | 28.0 ms | 같음 |

클라이언트는 100만 행 중 **한 행도 받지 못한다.** 서버는 10만 행을 넘길 때까지 읽고 JSON으로 만든 뒤 그 결과를 버린다(Phase 3 spec "결과 크기 제한"). 수십 ms를 쓰고 146바이트 오류만 돌려준다.

### 2. 전체 순회 `GET /users?limit=1000` (커서 0부터 `has_more: false`까지)

| 실행 | 받은 행 | 파일의 행 | 페이지 수 | 파일과 다른 행 | 순회 시간(참고) |
|---|---|---|---|---|---|
| 1 | 1,000,000 | 1,000,000 | 1000 | 0 | 2.0 s |
| 2 | 1,000,000 | 1,000,000 | 1000 | 0 | 1.9 s |

- 받은 행을 `users.tsv`의 각 줄과 순서대로 비교했다(`id TAB name TAB age`). 다른 행이 0이고 개수가 같으므로 중복·누락이 없다.
- 마지막 페이지(1000번째)에서 정확히 1000행이 남았다. N+1 판단 덕분에 그 페이지에서 바로 `has_more: false`가 나왔고, 빈 페이지를 한 번 더 요청하지 않았다(페이지 수 1000).
- 매 페이지의 `next_cursor`가 그 페이지 마지막 행의 id인지도 확인했다.
- 순회 시간은 확인 항목이 아니다(D10). 요청 1000개를 하나씩 순서대로 보낸 시간이다.

### 3. 페이지 응답 시간과 바이트 (각 30회)

실행 1:

| limit | 위치 | after_id | 행 | has_more | 응답 바이트 | 중앙값 | p90 |
|---|---|---|---|---|---|---|---|
| 100 | 첫 페이지 | 0 | 100 | true | 2,168 | 0.35 ms | 0.48 ms |
| 100 | 중간 페이지 | 500000 | 100 | true | 2,627 | 0.30 ms | 0.41 ms |
| 100 | 마지막 페이지 | 999900 | 100 | false | 2,602 | 0.30 ms | 0.38 ms |
| 1000 | 첫 페이지 | 0 | 1000 | true | 22,215 | 0.52 ms | 0.71 ms |
| 1000 | 중간 페이지 | 500000 | 1000 | true | 25,367 | 0.63 ms | 0.90 ms |
| 1000 | 마지막 페이지 | 999000 | 1000 | false | 25,342 | 0.55 ms | 0.65 ms |

실행 2:

| limit | 위치 | 중앙값 | p90 |
|---|---|---|---|
| 100 | 첫 / 중간 / 마지막 | 0.34 / 0.26 / 0.26 ms | 0.44 / 0.32 / 0.35 ms |
| 1000 | 첫 / 중간 / 마지막 | 0.53 / 0.55 / 0.53 ms | 0.64 / 0.65 / 0.64 ms |

바이트 차이는 id 자릿수 때문이다. 첫 페이지는 id가 1~100이라 짧고, 중간·마지막은 6~7자리다.

## 해석 (계측값과 추정을 나눔)

**계측값:**
- 같은 데이터·같은 서버에서 전체 조회는 실패하고(400, 146바이트), 페이지로는 100만 행 전부를 파일과 같게 받았다.
- 페이지 하나는 0.3~0.6 ms, 2~25 KB였다. **첫 페이지와 마지막 페이지의 응답 시간이 같은 수준**이었다(limit 100: 0.26~0.35 ms, limit 1000: 0.52~0.63 ms, 두 실행 모두).
- limit 100 → 1000(행 10배)일 때 응답 시간은 약 1.6~2배였다.

**추정(이번에 재지 않은 것):**
- 위치와 상관없이 시간이 같은 것은, 시작 위치를 B+ 트리로 찾고(높이 4, Phase 2) 그 뒤 `limit`줄만 읽기 때문으로 본다. 단위 테스트로 "파일에서 읽은 줄 수 = `min(limit, 남은 행)`"은 확인했지만(E1), 시간을 단계별로 나눠 재지는 않았다.
- 행이 10배인데 시간이 2배 정도인 것은, 요청마다 드는 고정 비용(연결, 파이썬 처리, HTTP 파싱)이 행 처리 비용보다 크기 때문으로 본다. 나눠 재지 않았다.
- 실제 네트워크라면 응답 바이트가 큰 limit 1000의 전송 시간 차이가 더 커질 수 있다. 재지 않았다.
- OFFSET 방식과의 비교는 이번 범위가 아니다(spec "제외"). OFFSET이었다면 뒤쪽 페이지일수록 건너뛸 행을 읽어야 해서 느려질 것으로 예상하지만, 재지 않았다.

## 다시 재는 방법

```bash
docker run --rm -v "$PWD:/src:ro" gcc:13 bash -c "cp -r /src /w && cd /w && make page-bench"
# 행 수·반복 횟수 바꾸기: make page-bench PAGE_ROWS=200000 PAGE_REPEAT=10
```

결과 표는 `build/page_result.md`에도 쓴다. 세 가지 확인 중 하나라도 어긋나면(전체 조회가 실패하지 않음, 순회 결과가 파일과 다름) 종료 코드 1로 끝난다.
