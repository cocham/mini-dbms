# Phase 5 개발 명세 — 커서 페이지 조회 (`GET /users`)

## 목표

클라이언트가 **데이터가 많아도 목록을 끝까지 받을 수 있게** 한다.

지금 서버는 SELECT 결과를 한 응답에 모은다. 결과가 상한(기본 100,000행 또는 8 MiB)을 넘으면 그 결과를 통째로 버리고 `RESULT_TOO_LARGE`(400)로 답한다(Phase 3 spec "결과 크기 제한"). 100만 행에서 `SELECT * FROM users;`는 받을 수 없다. `WHERE id BETWEEN a AND b`로 나눠 받을 수는 있지만, 삭제로 id에 빈 곳이 생기면 페이지가 덜 차거나 비고, 다음 페이지가 있는지도 알 수 없다.

이번 Phase는 이 실패를 다음처럼 바꾼다.

```text
지금     전체 목록 요청 → 결과가 너무 많음 → 오류
바뀐 뒤  GET /users?limit=100              → 100행 + next_cursor
         GET /users?after_id=<커서>&limit=100 → 이어지는 100행
         ... has_more가 false가 될 때까지
```

핵심은 **엔진이 필요한 만큼만 읽고 멈추는 것**이다. 전체를 읽은 뒤 잘라 보내면 조회 비용은 그대로다. B+ 트리로 시작 위치를 찾고, 리프 연결을 따라 정해진 행 수만 읽는다.

## 결정 상태

- [확정: 사용자, 2026-11-18] **범위는 `GET /users` 커서 페이지 조회와 엔진의 제한 읽기**다. SQL에 `LIMIT`·`OFFSET`을 더하는 확장은 하지 않는다. `POST /query`와 CLI는 바뀌지 않는다(DB-P5-D01).
- [확정: 사용자, 2026-11-18] **`has_more`는 N+1행으로 판단한다.** 요청한 `limit`보다 한 행을 더 읽어 보고, 있으면 `true`다. 그 한 행은 응답에 넣지 않는다(DB-P5-D02).
- [확정: 사용자, 2026-11-18] **`next_cursor`는 이번 응답에 넣은 마지막 행의 id**다(DB-P5-D03).
- [확정: 사용자, 2026-11-18] **페이지를 넘기는 사이의 변경에 대해 전체 스냅샷은 보장하지 않는다.** 각 페이지는 그 요청 시점의 데이터다. 보장은 **커서 0에서 시작해 돌려받은 커서를 따라가는 순방향 조회**로 한정한다. 같은 페이지를 다시 요청했을 때의 exactly-once 전달은 보장하지 않는다(DB-P5-D04).
- [확정: 사용자, 2026-11-18] **`limit`이 계산된 페이지 상한을 넘으면 거절한다.** 상한은 JSON 최악 크기와 응답 고정 부분을 반영해 계산하고, 기본 `limit`도 그 상한 이하로 맞춘다. 실패 방지는 **결과 크기 상한에 걸리는 실패**에 한정한다(DB-P5-D08).
- [확정: 사용자, 2026-11-18] **측정은 변경 없는 100만 행에서** 전체 조회 실패, 페이지 전체 순회의 정확성, 페이지 응답 시간과 바이트를 확인한다(DB-P5-D10).
- [확정: 사용자, 2026-11-18] design.md의 나머지 결정(D03 빈 페이지 `null`, D05 파라미터, D06 검증·`INVALID_PARAM`, D07 엔진 인터페이스, D09 응답 형식, D11 진행)은 추천대로 확정했다. 본문의 `[확정: D0n]` 표시가 그 항목이다.
- [유지] 진행 방식: 문서 확정 → 구현 → 테스트·검사 → 커밋 → 사용자 검증(PASS) → push와 main 대상 PR. P5-01~P5-03은 이어서 만들고 한 번에 검증받되, **단위마다 그 단위의 테스트는 실행해 통과시킨 뒤** 다음 단위로 간다(D11).

## API 계약

### 요청

```http
GET /users?after_id=200&limit=100
```

| 파라미터 | 의미 | 기본값 | 허용 범위 |
|---|---|---|---|
| `after_id` | 이 id **보다 큰** 행부터 준다. 첫 페이지는 생략하거나 0 | 0 [확정: D05] | 0 이상 `INT64_MAX` 이하의 10진 정수 |
| `limit` | 이번 페이지에 받을 최대 행 수 | `min(100, 페이지 상한)` [확정: D05, D08] | 1 이상 **페이지 상한** 이하. 페이지 상한은 기본 설정에서 1000(아래 "응답 상한과의 관계") [확정: D05, D08] |

- `after_id`로 준 id의 행이 **없어도 된다.** 지워졌거나 처음부터 없던 id여도 "그보다 큰 첫 행"부터 준다. 그래서 커서로 받은 행이 그사이 지워져도 다음 요청이 실패하지 않는다.
- 메서드는 `GET`만 받는다. 다른 메서드는 405 `METHOD`(`Allow: GET`).
- 요청 본문은 읽기는 하지만 쓰지 않는다(무시). 크기 상한(1 MiB)은 다른 요청과 같다.
- `POST /query`와 같은 HTTP 규칙을 따른다. 연결 하나에 요청 하나, `Connection: close`, 요청 대상에 보이는 ASCII만 허용 등이다.

### 입력 검증 [확정: D06]

아래는 모두 400 `INVALID_PARAM`이고, 엔진을 부르지 않는다. 오류 메시지는 어떤 파라미터가 왜 틀렸는지 알려 준다. 페이지 상한을 넘은 경우에는 상한값도 알려 준다.

| 입력 | 예 | 이유 |
|---|---|---|
| 숫자가 아닌 값, 빈 값 | `limit=abc`, `limit=`, `after_id=1.5` | 10진 정수만 받는다 |
| 부호 | `after_id=-1`, `limit=+10` | id는 양수, after_id는 0 이상. `+`도 받지 않는다 |
| 범위 밖 | `limit=0`, `limit=1001`, `after_id=9223372036854775808` | 위 표의 허용 범위 |
| 모르는 파라미터 | `limt=10`, `offset=5` | 오타를 조용히 무시하면 클라이언트는 원하던 페이지를 받았다고 착각한다 |
| 같은 파라미터 두 번 | `limit=10&limit=20` | 어느 값을 쓸지 모호하다 |
| `=`가 없는 항목 | `?limit` | 값이 없다 |
| 퍼센트 인코딩 | `limit=%31%30` | 디코딩하지 않는다. 값은 숫자뿐이라 인코딩할 일이 없다. 숫자가 아니므로 거부 |

- 앞에 붙은 0(`limit=010`, `after_id=007`)은 거부한다. `0` 하나는 허용한다(`after_id=0`). 19자리를 넘는 숫자는 거부한다.
- `?`만 있거나 쿼리 문자열이 비어 있으면 모든 값이 기본값이다.
- 쿼리 문자열 전체 길이에도 상한을 둔다(제안 256바이트, 넘으면 400 `INVALID_PARAM`). 파라미터 두 개면 충분하다.

### 응답 [확정: D09]

`200`, `Content-Type: application/json; charset=utf-8`

```json
{"ok":true,"columns":["id","name","age"],"rows":[[201,"민수",25],[205,"Kim",30]],"has_more":true,"next_cursor":205}
```

| 필드 | 의미 |
|---|---|
| `columns`, `rows` | `POST /query`의 select 결과와 같은 형식. `rows`는 id 오름차순 |
| `has_more` | `true`면 `next_cursor` 뒤에 행이 더 있다(이번 요청 시점에 한 행을 더 읽어 확인함). `false`면 이번 요청 시점에는 더 없다 |
| `next_cursor` | `rows`의 마지막 행 id. 다음 요청의 `after_id`로 그대로 쓴다. **`rows`가 비었으면 `null`** [확정: D03] |

- 문자열 이스케이프, 올바르지 않은 UTF-8의 대체 문자 처리는 `POST /query`와 같다.
- id는 JSON 숫자다(`/query`와 같음). JavaScript 숫자는 2^53까지만 정확하므로, id가 그보다 커지면 JS 클라이언트에서 값이 바뀔 수 있다. 이번 범위에서 다루지 않는다(id는 1씩 증가하므로 현실적으로 도달하지 않는다).

### 경우별 동작

| 경우 | 조건 | 응답 |
|---|---|---|
| 첫 페이지 | `after_id` 생략 또는 0 | id가 가장 작은 행부터 최대 `limit`행 |
| 중간 페이지 | `after_id` 뒤에 `limit`행보다 많이 남음 | `limit`행, `has_more: true`, `next_cursor` = 마지막 행 id |
| **마지막 페이지** | `after_id` 뒤에 1~`limit`행이 남음 | 남은 행 전부, `has_more: false`, `next_cursor` = 마지막 행 id. **정확히 `limit`행이 남은 경우도** N+1번째 행이 없으므로 `false`다. 그래서 클라이언트가 빈 페이지를 한 번 더 요청할 필요가 없다 |
| **빈 페이지** | 테이블이 비었거나, `after_id`가 가장 큰 id 이상 | `rows: []`, `has_more: false`, `next_cursor: null` |
| `after_id = INT64_MAX` | 그보다 큰 id는 없음 | 빈 페이지(위와 같음). `after_id + 1` 계산이 넘치지 않게 따로 처리한다 |
| **삭제로 생긴 id 공백** | 예: id 1~10 중 3·4·5 삭제, `limit=3` | `limit`은 **행 수**지 id 폭이 아니다. 첫 페이지는 `[1,2,6]`, 다음은 `[7,8,9]`, 그다음은 `[10]`이고 `has_more: false`. 공백 때문에 페이지가 덜 차지 않는다 |
| `after_id`의 행이 이미 지워짐 | 커서 7을 받은 뒤 id 7 삭제 | 실패하지 않는다. 7보다 큰 첫 행부터 준다 |
| 중단 상태 | 엔진이 `HALTED` | 503 `HALTED`(`/query`와 같은 이유·`reason`) |
| 종료 중 | 큐에서 기다리던 연결 | 503 `SHUTTING_DOWN`(accept 스레드의 고정 응답, Phase 3와 같음) |

### 정상 조기 종료

- 엔진은 B+ 트리로 `after_id`보다 큰 첫 키의 리프를 찾고, 리프 연결을 따라 **최대 `limit + 1`행만** 읽은 뒤 멈춘다. 이 멈춤은 **오류가 아니다.**
- 지금 범위 조회에서 결과 콜백이 멈추라고 하면 `DBE_SINK` 오류("조회 결과 처리에 실패했습니다")가 된다. 페이지 조회는 이 경로를 쓰지 않고, 정해진 행 수에 이르면 정상으로 끝난다 [확정: D07].
- "읽은 행 수"는 `limit + 1`과 남은 행 수 중 작은 값이다. 테스트 빌드에서 이 값을 세어 확인한다. 디스크에서 실제로 읽는 바이트는 읽기 버퍼(64 KiB) 단위라 행 수보다 많을 수 있다. 완료 기준은 행 수로 잡는다.
- 시작 위치를 찾는 비용은 트리 높이만큼이다(100만 행에서 높이 4, Phase 2). 그래서 첫 페이지와 뒤쪽 페이지의 엔진 비용이 같은 수준일 것으로 **예상**한다. P5-03에서 첫·중간·마지막 페이지의 응답 시간을 재서 확인한다(D10).

### 응답 상한과의 관계 [확정: D08]

기존 상한(`--max-rows`, `--max-response`)은 그대로 두고, `/users`는 **결과 크기 상한에 걸려 실패하는 일이 없도록 `limit`의 최대값을 미리 정한다.**

```text
페이지 상한 = min(1000, --max-rows, (--max-response − 고정 부분 최대) ÷ 한 행 최대)
기본 limit  = min(100, 페이지 상한)
```

- **한 행 최대 = 1,559바이트.** 최악의 경우를 더한 값이다.
  - `[`, id 19자리, `,` → 21
  - 이름: 따옴표 2 + 255바이트가 모두 `\u00XX`(6바이트)로 이스케이프되는 경우 1,530 → 1,532
  - `,`, age 3자리, `]` → 5
  - 행 사이 쉼표 1(모든 행에 붙는다고 보수적으로 셈)
- **고정 부분 최대 = 102바이트.** 앞 `{"ok":true,"columns":["id","name","age"],"rows":[`(49) + 뒤 `],"has_more":false,"next_cursor":9223372036854775807}`(53). `false`·19자리 커서처럼 가장 긴 경우로 센다.
- 두 값은 구현에서 상수로 두고, 최악의 행을 실제로 만들어 JSON 크기가 상수 이하인지 테스트로 확인한다.
- 계산 예:

  | 설정 | 바이트로 들어가는 행 | 페이지 상한 | 기본 limit |
  |---|---|---|---|
  | 기본(`--max-response 8388608`, `--max-rows 100000`) | 5,380 | **1000** | 100 |
  | `--max-rows 50` | 5,380 | 50 | 50 |
  | `--max-response 4096`(허용하는 최소값) | 2 | **2** | 2 |

- 페이지 상한은 서버가 시작할 때 한 번 계산하고, 시작 줄 로그에 함께 찍는다.
- `limit`이 페이지 상한을 넘으면 400 `INVALID_PARAM`이고, 메시지에 상한값을 넣는다. 조용히 줄이지 않는다.
- **실패 방지는 결과 크기 상한에 한정한다.** `/users`는 `RESULT_TOO_LARGE`를 돌려줄 일이 없다. 그 밖의 실패는 그대로 있을 수 있다: 응답을 만들 메모리가 없으면 500 `INTERNAL`, 읽기 오류·인덱스 불일치는 500 `STORAGE`, 503 `BUSY`·`HALTED`·`SHUTTING_DOWN`, 전송 실패·기한 초과.
- 상한들은 `/query`처럼 요청 단위다. `/users` 요청 하나는 페이지 하나다.

### 동시 변경과 보장 [확정: D04]

**각 페이지 하나는** 한 시점의 데이터다. 페이지 조회는 SELECT처럼 공유 잠금 안에서 실행되므로, 읽는 도중 끼어든 INSERT·UPDATE·DELETE를 보지 않는다(Phase 3 C2와 같음).

**페이지 사이에는 스냅샷이 없다.** 1페이지와 2페이지는 서로 다른 시점의 데이터일 수 있다.

**보장하는 조건 — 순방향 조회:** 클라이언트가 커서 0(`after_id` 생략 또는 0)에서 시작해, 매번 **직전 응답의 `next_cursor`를 다음 `after_id`로** 넘기며 `has_more: false`까지 따라가는 경우다. 이 조건에서는 id가 항상 증가하고, 지운 id를 다시 쓰지 않으며(Phase 4 D04), UPDATE로 id를 바꿀 수 없으므로(Phase 4 D07) 아래가 성립한다.

| 순회 중 일어난 일 | 클라이언트가 보는 것 |
|---|---|
| 순회를 시작할 때부터 끝날 때까지 **계속 있던 행** | **정확히 한 번** 나온다. 빠지지도 겹치지도 않는다 |
| 새로 INSERT된 행 | 새 id는 지금까지의 모든 id보다 크므로, 이미 받은 페이지에 끼어들지 않는다. 순회가 끝나기 전에 들어왔으면 뒤쪽 페이지에 나온다 |
| 아직 안 받은 범위에서 DELETE된 행 | 나오지 않는다 |
| 이미 받은 범위에서 DELETE된 행 | 클라이언트는 이미 받은 옛 값을 갖고 있다 |
| UPDATE된 행 | 그 행이 든 페이지를 읽은 시점의 값으로 나온다. 받은 뒤의 변경은 반영되지 않는다 |
| UPDATE·DELETE의 파일 다시 쓰기 | 영향 없다. 커서는 파일의 바이트 위치가 아니라 id라서, 다시 쓰기로 위치가 모두 바뀌어도 그대로 쓸 수 있다 |

- `has_more: false`는 "그 요청 시점에 더 없었다"는 뜻이다. 그 뒤에 들어온 행은 마지막 `next_cursor`로 다시 요청하면 받을 수 있다.

**보장하지 않는 것:**
- **전체 스냅샷.** 순회 전체를 한 시점으로 보고 싶다면(예: 합계를 정확히 맞춰야 할 때) 이 API로는 할 수 없다.
- **같은 페이지를 다시 요청했을 때의 exactly-once 전달.** 응답을 못 받아 같은 `after_id`로 다시 요청하면, 그 사이의 변경에 따라 다른 행 집합이 올 수 있다(새로 들어온 행이 끼거나, 지워진 행이 빠지거나, 바뀐 값이 오거나). 첫 요청의 응답이 실제로는 전달됐고 클라이언트가 그것도 처리했다면 같은 행을 두 번 처리하게 된다. 서버는 어떤 페이지를 누구에게 보냈는지 기억하지 않는다. 중복 처리를 피하는 것은 클라이언트 몫이다(예: 이미 처리한 가장 큰 id를 기억).
- **순방향이 아닌 사용.** 커서를 건너뛰거나(예: 직접 계산한 `after_id`), 받은 커서보다 작은 값으로 돌아가거나, 여러 순회를 섞는 경우.
