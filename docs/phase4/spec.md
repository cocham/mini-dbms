# Phase 4 개발 명세 — UPDATE·DELETE

## 목표

기존 엔진(Phase 1·2)과 API 서버(Phase 3)에 행 수정(`UPDATE`)과 행 삭제(`DELETE`)를 더한다. CLI와 서버 모두에서 쓸 수 있다.

## 결정 상태

- [확정: 사용자, 2026-11-18] **저장 방식은 파일 통째로 다시 쓰기**다. UPDATE·DELETE가 행을 바꾸면 바뀐 내용 전체를 임시 파일에 새로 쓰고, 원래 파일과 바꿔치기(rename)한다. 파일 형식(`id TAB name TAB age LF`)과 "id는 증가 순서" 규칙은 그대로다(DB-P4-D01).
- [확정: 사용자, 2026-11-18] **조회 결과는 항상 id 순서**다. 파일이 계속 id 순서로 유지되므로 지금 조회 경로가 그대로 id 순서를 낸다(DB-P4-D02).
- [확정: 사용자, 2026-11-18] **WHERE 없는 UPDATE·DELETE는 거부**한다(구문 오류, 아무것도 실행하지 않음). 표준 SQL과 다르다(DB-P4-D03).
- [확정: 사용자, 2026-11-18] design.md의 D04~D08(다음 id 보존, 실패 처리, 결과 행 수, 문법, 잠금)을 추천대로 확정했다. 아래 `[확정: D0n]` 표시가 그 항목이다.
- [확정: 사용자, 2026-11-18] **100만 행 측정은 하지 않는다.** 로직을 제대로 구현하는 데 집중한다. P4-04는 문서·실습만 한다.
- [유지] 진행 방식: 문서 확정 → 단위마다 구현 → 테스트·검사 → 커밋 → 사용자 검증(PASS) → 다음 단위. PASS 뒤 push와 main 대상 PR.
- [변경: 사용자, 2026-11-18] P4-02부터는 단계를 합쳐 P4-02~P4-04를 다 만든 뒤 한 번에 검증받는다.

## 문법 [확정: D07]

```sql
UPDATE users SET name = '새 이름' WHERE id = 3;
UPDATE users SET age = 31 WHERE age = 30;
UPDATE users SET name = 'Kim', age = 40 WHERE id BETWEEN 10 AND 20;
DELETE FROM users WHERE id = 7;
DELETE FROM users WHERE id >= 1000;
```

- `SET`에는 `name`, `age` 중 하나 또는 둘을 쓴다. 같은 컬럼을 두 번 쓰면 구문 오류다. `id`는 바꿀 수 없다(구문 오류).
- 값은 INSERT와 같은 규칙으로 검사한다: name은 1~255바이트, 탭·CR·LF 불가. age는 0~150 정수. 어긋나면 실행 오류이고 아무 행도 바뀌지 않는다.
- `WHERE`는 필수이고, SELECT와 같은 형태만 쓴다: `id = 값`, `age = 값`, `id < <= > >= 값`, `id BETWEEN a AND b`.
- 대소문자, 주석, 여러 줄, 문자열 이스케이프(`''`)는 지금 SQL과 같다.
- `EXPLAIN UPDATE`·`EXPLAIN DELETE`는 지원하지 않는다(구문 오류).

## 결과 [확정: D06]

바뀐 행 수 `n`을 돌려준다. 조건에 맞는 행이 없으면 `n = 0`이고 파일을 건드리지 않는다. UPDATE는 조건에 맞은 행 수를 센다(값이 원래와 같아도 1로 센다).

CLI:

```text
UPDATE 1
DELETE 0
```

서버(`POST /query`의 `results` 항목):

```json
{"type":"update","count":1}
{"type":"delete","count":0}
```

## 다음 id [확정: D04]

삭제된 id는 다시 쓰지 않는다. 가장 큰 id의 행을 지운 뒤에도 다음 INSERT는 그보다 큰 id를 받는다.

```text
INSERT ×3 → id 1, 2, 3
DELETE FROM users WHERE id = 3;
INSERT → id 4   (3을 다시 쓰지 않음)
```

## 동작과 성능

- UPDATE·DELETE 문장 하나는 파일 전체(100만 행이면 약 25 MB)를 다시 쓰고 인덱스를 새로 만든다. 그동안 서버는 배타 잠금을 잡으므로 **다른 모든 조회와 INSERT가 기다린다**. 걸리는 시간은 파일 크기에 비례하며, 이번 Phase에서는 재지 않는다. 바뀐 행이 0이면 다시 쓰지 않는다.
- 문장 하나는 원자적이다. 다시 쓰기가 끝나기 전에 실패하면 원래 파일과 인덱스가 그대로 남는다(일부 행만 바뀐 상태가 없다). 여러 문장에 걸친 트랜잭션은 여전히 없다.
- 디스크 동기화(`fsync`)는 하지 않는다(Phase 3와 같은 제외 항목). 전원이 꺼지면 바꿔치기가 디스크에 남았는지 보장하지 않는다.

## 실패와 재시도 [확정: D05]

| 경우 | 데이터 | 응답(서버) | 다시 보내도 되나 |
|---|---|---|---|
| 구문 오류, WHERE 없음 | 아무것도 실행 안 됨 | 400 `SQL_SYNTAX` | 고쳐서 다시 |
| 값 검증 실패(age 200 등) | 이 문장은 아무것도 안 바뀜, 앞 문장은 실행됨 | 400 `SQL_ERROR` | `statement` 번호부터 |
| 임시 파일 쓰기·바꿔치기 실패(디스크 가득 참 등) | 이 문장은 아무것도 안 바뀜(원래 파일 그대로) | 500 `STORAGE` | 원인을 고친 뒤 `statement` 번호부터 |
| 바꿔치기 뒤 파일 다시 열기 실패(Windows CLI에서만 생길 수 있음, design.md) | 파일에는 반영됨, 프로세스는 계속 쓸 수 없음 | CLI 오류 종료 | 다시 실행하면 파일에서 복원. 이 문장은 이미 반영됐으므로 다시 실행하기 전에 SELECT로 확인한다(아래) |

**재시도와 "같은 문장을 다시 실행하기"** — 무조건 안전하지 않다. 경우를 나눈다.

| 상황 | 데이터 | 돌려받는 행 수 |
|---|---|---|
| 첫 실행과 재실행 사이에 **다른 쓰기가 없었다** (예: CLI 혼자 실행) | 첫 실행 직후와 같다. SET 값이 상수이고 조건이 id·age뿐이라, 첫 실행 뒤 조건에 맞는 행은 이미 SET 값을 가졌거나(UPDATE) 이미 없다(DELETE) | **달라질 수 있다.** DELETE는 두 번째에 보통 0이다. `UPDATE users SET age = 31 WHERE age = 30`도 두 번째에는 0이다. `SET name = 'x' WHERE id = 3`처럼 조건 컬럼을 바꾸지 않는 UPDATE는 같은 수다 |
| 사이에 **다른 클라이언트의 쓰기가 끼어들 수 있다** (서버) | **새 데이터를 바꿀 수 있다.** 예: `DELETE FROM users WHERE age = 30` 성공 → 다른 요청이 age 30인 행을 INSERT → 같은 DELETE를 다시 보내면 그 새 행도 지운다. UPDATE도 그 사이에 조건에 맞게 된 행이나 다른 클라이언트가 고친 행을 덮어쓴다 | 달라질 수 있다 |

그래서 "응답을 못 받아 반영 여부를 모르는" 경우의 권장은 INSERT와 같다: **먼저 SELECT로 현재 상태를 확인하고 다시 보낼지 정한다.** `WHERE id = 값`처럼 특정 행만 가리키는 문장은 끼어든 쓰기의 영향이 그 행 하나로 줄지만, 다른 클라이언트가 그 행을 고쳤다면 재시도가 그 변경을 덮어쓰는 것은 마찬가지다. 엔진에는 "이 요청을 이미 처리했는지"를 기억하는 장치(요청 id 등)가 없고, 이번 범위도 아니다.
