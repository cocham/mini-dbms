# Phase 6 개발 명세 — age 조건 페이지 조회 (선형 탐색 기준선 → age 보조 인덱스)

## 목표

클라이언트가 **조건에 맞는 행만 페이지로** 받을 수 있게 하고, 그 비용이 어디서 생기는지 **숫자로 드러낸다.**

Phase 5의 `GET /users`는 id 순서 전체 목록만 준다. id는 B+ 트리에 있으므로, 엔진은 시작 위치를 찾은 뒤 필요한 행만 읽고 멈춘다. 페이지 비용은 페이지 위치와 상관없이 일정했다(Phase 5 benchmark: 0.26~0.63 ms).

이번에는 조건 하나를 더한다.

```http
GET /users?age=30&limit=100
GET /users?age=30&after_id=<커서>&limit=100
```

age에는 인덱스가 없다. 엔진은 커서 뒤의 행을 하나씩 파일에서 읽어 age를 확인해야 한다. 그래서 **돌려준 행 수와 엔진이 검사한 행 수가 달라진다.** 맞는 행이 드물면 100행을 채우려고 파일 대부분을 읽는다. 마지막 페이지는 "더 없음"을 확인하려고 파일 끝까지 읽는다.

이번 Phase는 두 단계로 나눈다. **최종 목표는 age 보조 인덱스로 같은 요청을 개선하고, 같은 요청의 개선 전후를 비교하는 것**이다(발표 구성: [README.md](README.md)).

1. **기준 구현(선형 탐색).** 가장 단순한 방식으로 조건 페이지 조회를 만들고, 요청마다 "파일에서 읽고 확인한 행 수"를 계측한다. 이 경로는 개선 뒤에도 지우지 않고 비교 기준으로 남긴다.
2. **age 보조 인덱스(후속 단위).** age가 같은 행들의 id를 id 순서로 찾는 별도 경로를 더한다. 반환 값·순서·커서·`has_more`의 의미는 기준 구현과 같아야 한다.
3. **대표 실험 하나.** 변경 없는 같은 데이터에서 age 조건이 드문 요청 하나를 두 경로로 실행해, 결과가 같은지 확인하고 파일 행 확인 수와 클라이언트 응답 시간 중앙값을 비교한다.

## 결정 상태

- [확정: 사용자, 2026-11-18] **범위는 `age = 값` 필터 하나**다. 결과는 id 오름차순이고, 커서는 Phase 5와 같은 id 커서(`after_id`, `next_cursor`)다. **필터 없는 `/users`의 동작은 그대로다**(DB-P6-D01).
- [확정: 사용자, 2026-11-18] **`has_more`는 조건에 맞는 `limit + 1`번째 행이 있는지로 판단한다**(DB-P6-D02).
- [확정: 사용자, 2026-11-18] **"검사한 행 수"를 계측한다.** 반환 행 수와 별도로, 조건 판정을 위해 읽은 행 전부를 센다. `has_more` 확인을 위해 더 읽은 행도 포함한다. **응답 시간(JSON 생성·통신 포함)과 엔진 탐색량은 구분한다.** 구체적인 정의·노출 방식은 D08~D10에서 정한다.
- [확정: 사용자, 2026-11-18, 수정] **측정은 대표 실험 하나다.** 변경 없는 같은 데이터에서 age 조건이 드문 요청 하나를 선형 탐색과 age 인덱스로 실행한다. 데이터·요청·서버 설정은 같게 두고, 반환 행과 내용이 같은지, 파일에서 읽고 확인한 행 수(N+1 확인 포함), 같은 요청 반복의 클라이언트 응답 시간 중앙값을 비교한다. 데이터 분포·환경·반복 횟수를 기록한다. 네 가지 분포 전체 실험은 제외한다(DB-P6-D11·D12). 조건을 유지한 순방향 조회의 정확성과 기존 기능 회귀는 테스트로 확인한다.
- [확정: 사용자, 2026-11-18] **동시 변경 시 전체 스냅샷은 보장하지 않는다**(Phase 5 D04와 같은 방식, 아래 "동시 변경과 보장").
- [확정: 사용자, 2026-11-18, 수정] **age 보조 인덱스는 기준 구현 뒤의 후속 단위로 만든다.** 만들지 않는 것: 새 정렬(age 순 등), 탐색 예산 제한, OFFSET 비교. 쓰기 성능과 추가 메모리는 측정하지 않으면 수치상 성과로 말하지 않고, 추가 유지 작업과 한계로 설명한다.
- [확정: 사용자, 2026-11-18, 수정] **단위마다 멈춘다.** 각 기능 단위의 구현·테스트가 끝나면 Codex 검증을 기다리고, PASS 뒤에만 그 변경을 커밋·푸시한다. 다음 단위는 사용자가 진행하라고 할 때 시작한다. main에는 직접 커밋·푸시하지 않는다(DB-P6-D13).
- [확정: 사용자, 2026-11-18] 입력·오류 계약(D03~D05), 엔진 인터페이스(D06·D07), 계측 정의(D08~D10), 대표 실험(D11·D12), age 인덱스 구조·행 연결·유지·경로 선택(D14~D17)은 design.md의 추천안으로 확정했다. 본문의 `[확정: D0n]` 표시가 그 항목이다.

## API 계약

### 요청

```http
GET /users?age=30&after_id=200&limit=100
```

| 파라미터 | 의미 | 기본값 | 허용 범위 |
|---|---|---|---|
| `age` | 이 값과 age가 **같은** 행만 준다 | 없음(생략하면 필터 없음 = Phase 5 동작) | 0 이상 150 이하의 10진 정수 [확정: D03, D04] |
| `after_id` | Phase 5와 같다. 이 id보다 큰 행부터 찾는다 | 0 | 0 이상 `INT64_MAX` 이하 |
| `limit` | Phase 5와 같다. 이번 페이지에 받을 최대 행 수 | `min(100, 페이지 상한)` | 1 이상 페이지 상한 이하 |

- 세 파라미터의 순서는 상관없다.
- 페이지 상한은 Phase 5와 같다(기본 설정 1000). 한 행의 JSON 최악 크기가 바뀌지 않기 때문이다.
- `age`가 없으면 Phase 5와 **같은 경로**로 처리한다. 응답 본문은 바이트 단위로 같다. 계측 헤더만 더해진다 [확정: D09].

### 입력 검증 [확정: D03, D04]

Phase 5의 규칙(400 `INVALID_PARAM`, 엔진을 부르지 않음)을 그대로 따르고, `age`에 같은 규칙을 적용한다.

| 입력 | 예 | 처리 |
|---|---|---|
| 숫자가 아닌 값, 빈 값 | `age=abc`, `age=`, `age=30.0` | 400 |
| 부호, 앞자리 0 | `age=-1`, `age=+30`, `age=030` | 400. `age=0`은 허용 |
| **범위 밖** | `age=151`, `age=999` | **400**. 저장된 age는 항상 0~150이라 맞는 행이 있을 수 없다. 클라이언트의 실수일 가능성이 높다 [확정: D04] |
| 같은 파라미터 두 번 | `age=30&age=40` | 400. "30 또는 40"으로 읽히지 않게 한다 |
| 모르는 파라미터 | `name=kim`, `age_min=30` | 400. 메시지가 받는 이름 세 개(`after_id`, `limit`, `age`)를 알려 준다 |

- 오류 메시지는 어떤 파라미터가 왜 틀렸는지 알려 준다.
- 검증 순서와 중단 상태의 처리는 Phase 5와 같다. 입력이 틀리면 엔진이 중단 상태여도 400이다.

### 응답

본문은 Phase 5와 같은 형식이다.

```json
{"ok":true,"columns":["id","name","age"],"rows":[[202,"user000202",30],[204,"user000204",30]],"has_more":true,"next_cursor":204}
```

| 필드 | 의미 |
|---|---|
| `rows` | age가 요청 값과 같은 행. id 오름차순, 최대 `limit`행 |
| `has_more` | `true`면 `next_cursor` 뒤에 **조건에 맞는** 행이 더 있다. 이번 요청에서 그 행 하나를 실제로 찾아 확인했다 |
| `next_cursor` | `rows`의 마지막 행 id. `rows`가 비었으면 `null`(Phase 5와 같음) |

계측 헤더 [확정: D09, D10, D16]. 200 응답에만 붙는다(400·503 등에는 없음). 아래는 선형 탐색으로 띄운 서버(`--age-path scan`)의 예다.

```http
X-Rows-Examined: 202
X-Rows-Examined-After-Last: 2
X-Age-Index-Keys: 0
X-Access-Path: scan
X-Engine-Us: 85
```

| 헤더 | 의미 |
|---|---|
| `X-Rows-Examined` | 이번 요청에서 엔진이 파일에서 읽어 확인한 행 수(E). `has_more` 확인을 위해 더 읽은 행도 포함한다 |
| `X-Rows-Examined-After-Last` | 그중 **마지막 반환 행 뒤에서** 읽은 행 수(T). `rows`가 비었으면 `X-Rows-Examined`와 같다 |
| `X-Age-Index-Keys` | age 인덱스에서 차례로 본 항목 수(K). 아래 "age 보조 인덱스 → 계측" |
| `X-Access-Path` | 실제로 실행된 경로: `id`(조건 없음), `scan`, `age-index` |
| `X-Engine-Us` | 서버가 엔진 호출(`db_page`)에 쓴 시간(마이크로초). 아래 "계측 정의" |

요청 로그 줄에도 같은 값이 붙는다. 예: `[요청] GET /users → 200, scan R=3 E=8 T=2 K=0 엔진 12 us, 0.31 ms`.

### 경우별 동작

`limit = L`, 조건은 `age = a`라고 하자.

| 경우 | 조건 | 응답 |
|---|---|---|
| 중간 페이지 | 커서 뒤에 맞는 행이 `L`개보다 많음 | 맞는 행 `L`개, `has_more: true`. 엔진은 `L + 1`번째로 맞는 행을 찾을 때까지 읽는다 |
| **마지막 페이지** | 커서 뒤에 맞는 행이 1~`L`개 | 남은 맞는 행 전부, `has_more: false`. 엔진은 **파일 끝까지** 읽어야 "더 없음"을 안다. 맞는 행이 정확히 `L`개 남아도 같다 |
| **일치 없음** | 커서 뒤에 맞는 행이 없음 | `rows: []`, `has_more: false`, `next_cursor: null`. 엔진은 커서 뒤를 **전부** 읽는다 |
| 빈 범위 | 테이블이 비었거나 `after_id ≥ 최대 id`, `INT64_MAX` | 빈 페이지. 검사한 행 0 |
| 커서가 맞지 않는 행·지워진 행 | `after_id`의 행이 지금 age `a`가 아니거나 없음 | 실패하지 않는다. `after_id`보다 큰 첫 행부터 검사한다 |
| 중단 상태 등 | | Phase 5와 같다(503 `HALTED`, 500 `STORAGE` 등) |

- **응답 시간에 상한이 없다.** 한 요청이 최대 테이블 전체를 읽는다. 탐색 예산 제한은 이번 범위에서 만들지 않는다. 이 비용을 재는 것이 이번 Phase의 목적이다.
- 긴 탐색 동안 공유 잠금을 쥐고 있다. 그동안 INSERT·UPDATE·DELETE는 기다린다. 이번 측정은 변경 없는 데이터라 이 대기를 재지 않는다. 결과를 해석할 때 고려할 비용으로만 적어 둔다.

### 계측 정의 [확정: D08, D10]

**엔진 탐색량(행 수)** — 결정적인 값이다. 같은 데이터·같은 요청이면 항상 같다.

| 이름 | 정의 |
|---|---|
| 반환 행 R | 응답 `rows`의 행 수 |
| 검사한 행 E | 이번 요청에서 엔진이 파일에서 읽고 age를 비교한 행 수. 커서 다음 행부터, ① `L + 1`번째로 맞는 행을 찾은 곳 또는 ② 파일 끝까지 |
| 마지막 반환 행 뒤 검사 T | E 중 마지막 반환 행보다 id가 큰 행 수. `has_more: true`면 `L + 1`번째로 맞는 행까지 포함한다. R = 0이면 T = E |

- **필터 없는 요청:** E = R, T = 0이다. Phase 5처럼 `L + 1`번째는 인덱스 키로만 확인하고 그 줄은 읽지 않기 때문이다.
- **T의 뜻:**
  - `has_more: true`면 T는 **다음 페이지가 다시 검사할 행 수**다. 다음 요청은 마지막 반환 행 뒤부터 다시 시작하기 때문이다.
  - `has_more: false`면 T는 "더 없음"을 확인하려고 읽은 꼬리의 길이다.
- 읽은 바이트는 세지 않는다. 행 하나는 줄 하나이고, 디스크 읽기는 64 KiB 버퍼 단위라 행 수가 더 정확한 기준이다.

**시간** — 측정마다 달라지는 값이다. 두 가지를 구분한다.

| 이름 | 재는 곳 | 들어가는 것 |
|---|---|---|
| 엔진 시간 | 서버, `db_page` 호출 앞뒤(`X-Engine-Us`) | 잠금 대기 + 탐색(파일 읽기·파싱·age 비교) + 맞는 행의 JSON 추가(최대 `L`행). 요청 파싱, 응답 머리와 꼬리, 전송은 들어가지 않는다 |
| 응답 시간 | 클라이언트(측정 도구) | 연결 → 요청 보내기 → 응답 끝까지 받기. 엔진 시간 + 큐 대기 + JSON 마무리 + 전송 + 클라이언트 처리 |

- 맞는 행의 JSON 추가는 엔진 콜백 안에서 일어나므로 엔진 시간에 들어간다. 그 몫은 같은 `L`의 **필터 없는 페이지** 엔진 시간을 넘지 않는다. 필터 없는 페이지는 `L`행을 읽고 JSON으로 만드는 것이 전부이기 때문이다. 측정 결과에 이 값을 함께 적어 비교 기준으로 쓴다.
- 변경 없는 데이터에서는 잠금 대기가 거의 없다(측정 중 쓰기 요청 없음).

### 동시 변경과 보장

Phase 5 D04와 같은 틀이다. **각 페이지 하나는** 공유 잠금 안의 한 시점이다. 페이지 사이에는 스냅샷이 없다.

**보장하는 조건 — 조건을 유지한 순방향 조회:** 커서 0에서 시작해 **같은 `age` 값을 유지하면서** 직전 응답의 `next_cursor`를 다음 `after_id`로 넘기며 `has_more: false`까지 따라가는 경우다.

| 순회 중 일어난 일 | 클라이언트가 보는 것 |
|---|---|
| 순회 시작부터 끝까지 **계속 있었고 age가 계속 `a`였던 행** | **정확히 한 번** 나온다 |
| 받은 행 | 그 페이지를 읽은 시점에 age가 `a`였다. id는 엄격하게 증가한다(겹침 없음) |
| 순회 중 age가 `a`로 바뀌었거나 `a`에서 다른 값으로 바뀐 행 | 나올 수도, 안 나올 수도 있다. 그 행이 든 범위를 읽은 시점의 값에 따른다 |
| 새로 INSERT된 age `a`인 행 | Phase 5와 같다. 이미 받은 범위에 끼어들지 않고, 순회가 끝나기 전이면 뒤쪽 페이지에 나온다 |

**보장하지 않는 것:** 전체 스냅샷, 같은 페이지 재요청의 exactly-once 전달, 순방향이 아닌 사용(Phase 5와 같음). 추가로 **순회 도중 `age` 값을 바꾸는 사용**도 보장하지 않는다. 커서는 id일 뿐이라 서버는 이전 요청의 조건을 모른다 [확정: D05].

## age 보조 인덱스 (후속 단위, P6-04·P6-05)

기준 구현을 마치고 검증받은 뒤 만든다. 구조와 유지 방식은 design.md D14~D17에서 정한다.

### 같아야 하는 것

age 인덱스 경로는 **기준 구현(선형 탐색)과 같은 요청에 같은 응답 본문**을 돌려준다. 같은 데이터·같은 `age`·`after_id`·`limit`이면 다음이 모두 같다.

- `rows`: 행 집합, 값, id 오름차순
- `next_cursor`: 마지막 반환 행 id, 빈 페이지면 `null`
- `has_more`: 조건에 맞는 `limit + 1`번째 행이 있는지
- 입력 검증·오류 응답

달라지는 것은 계측 헤더(검사량·시간)뿐이다.

### 계측 [확정: D16]

| 이름 | 헤더 | 선형 탐색 | age 인덱스 |
|---|---|---|---|
| 파일 행 확인 E | `X-Rows-Examined` | 커서 뒤에서 읽고 age를 비교한 행 전부(N+1 확인 포함) | 인덱스가 고른 id의 행만 읽음. 읽은 행의 age를 다시 확인한다. N+1은 인덱스의 다음 항목으로 판단하므로 그 행은 읽지 않는다 |
| 마지막 반환 행 뒤 확인 T | `X-Rows-Examined-After-Last` | spec "계측 정의"와 같음 | 0(빈 페이지면 E = 0) |
| age 인덱스 항목 확인 K | `X-Age-Index-Keys` | 0 | age 인덱스에서 커서 뒤로 차례로 본 항목 수(N+1 항목 포함). 시작 위치를 찾는 이진 탐색·트리 내려가기는 세지 않는다 |
| 실행 경로 | `X-Access-Path` | `scan` | `age-index` |

- 인덱스 키 확인(K)과 파일 행 확인(E)은 **섞어 세지 않는다.** id 인덱스로 행 위치를 찾는 횟수는 R과 같으므로 따로 헤더를 두지 않는다.
- 필터 없는 요청은 `X-Access-Path: id`, K = 0이다.

### 데이터와 인덱스의 일치 [확정: D15, D16]

- INSERT·UPDATE·DELETE·파일 다시 쓰기·재시작 뒤에도 age 인덱스의 내용은 "파일에서 age가 a인 id 전부, 오름차순"과 같아야 한다.
- 인덱스 경로가 읽은 행의 age가 요청 값과 다르거나 id가 다르면, 엉뚱한 행을 돌려주지 않고 500 `STORAGE`(인덱스 불일치)로 답한다. id 인덱스의 기존 재확인과 같은 원칙이다.
- 테스트 빌드에는 age 인덱스를 파일 전체 탐색 결과와 비교하는 검증 함수를 둔다.

### 대표 실험 [확정: D11, D12]

| 항목 | 값 |
|---|---|
| 데이터 | 변경 없는 100만 행. age 25는 1,000행(0.1%)이고, id가 1000으로 나눠 1이 남는 행(1, 1001, …, 999001)에 고르게 둔다. 나머지 행의 age는 20~69에서 25를 70으로 바꾼 값 |
| 요청 | `GET /users?age=25&after_id=0&limit=100` |
| 서버 | 같은 실행 파일, 같은 데이터 디렉터리, 기본 설정. 다른 것은 `--age-path scan` / `--age-path index` 하나(D17) |
| 기대값(계산) | 두 경로 모두 R = 100(id 1~99001), `has_more: true`, `next_cursor: 99001`. 선형 탐색 E = 100,001(1~100001번째 줄), T = 1,000. age 인덱스 E = 100, K = 101 |
| 반복 | 경로마다 워밍업 5회 뒤 30회, 순서를 바꿔 두 번(선형 → 인덱스 → 인덱스 → 선형). 클라이언트 응답 시간 중앙값, 엔진 시간 중앙값은 참고 |
| 확인 | 두 경로의 응답 본문이 바이트 단위로 같음. 헤더 E·T·K가 기대값과 같음 |

- 이 실험은 **읽기 하나의 비교**다. 쓰기 시간과 추가 메모리는 재지 않으므로 숫자로 말하지 않고, 유지 작업과 한계로 적는다.
- 응답 시간에는 연결·큐·JSON·전송이 들어간다. 검사량이 줄어든 배수만큼 시간이 줄어든다고 보지 않는다. 결과가 기대와 다르면 그대로 적는다.
