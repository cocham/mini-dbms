### 엔진 (D06, D07)

**D06 인터페이스 — 추천:** 기존 `table_page`·`db_page`를 넓힌다.

```c
/* storage.h */
typedef struct {
    int has_age; /* 0이면 필터 없음 */
    int age;
} PageFilter;

typedef struct {
    int has_more;
    int64_t rows_returned;      /* R */
    int64_t rows_examined;      /* E: 파일에서 읽어 조건을 검사한 행 (N+1 확인용 포함) */
    int64_t examined_after_last; /* T: E 중 마지막 반환 행 뒤 */
} PageStats;

/* filter가 NULL이거나 has_age가 0이면 Phase 5와 같은 경로(N+1은 키로만, E = R, T = 0).
 * 필터가 있으면 after_id + 1부터 줄을 읽어 age를 비교하고, 맞는 행 limit개를 fn에 넘긴 뒤
 * limit + 1번째로 맞는 행을 찾거나 끝에 이르면 멈춘다. st는 NULL이어도 된다. */
int table_page(Table *t, int64_t after_id, int64_t limit, const PageFilter *filter, RowFn fn, void *ctx,
               PageStats *st, DbError *err);

/* db.h — 같은 인자로 공유 잠금 안에서 table_page */
int db_page(Db *db, int64_t after_id, int64_t limit, const PageFilter *filter, RowFn fn, void *ctx,
            PageStats *st, DbError *err);
```

| 이유 | 다른 선택 |
|---|---|
| N+1·커서·빈 범위·`INT64_MAX` 처리가 한 함수에 있어서, 필터가 있든 없든 같은 규칙을 따른다. 통계 구조체 하나로 서버가 계측 헤더를 만들고, 단위 테스트가 R·E·T를 직접 확인한다(지금의 테스트 전용 카운터 두 개는 그대로 두고 F2 확인에 쓴다). 다음 단계에서 보조 인덱스를 넣을 때도 이 함수 안의 탐색 경로만 바꾸면 된다 | (가) `table_page_age`를 따로 둔다. 기존 함수는 안 건드리지만 N+1 처리가 두 벌이 되고, 필터 없는 요청의 계측(E = R)을 따로 맞춰야 한다. (나) 일반 조건자(`RowPred`)를 받는다. 확장은 쉽지만, 다음 단계에서 "age 조건이면 인덱스"를 판단하려면 결국 조건의 내용을 알아야 한다 |

- 바뀌는 호출: 서버 `handle_users`, 단위 테스트의 Phase 5 페이지 테스트(인자만 바뀜, 기대값 그대로).
- Executor·Parser는 이번에도 거치지 않는다(Phase 5 D07과 같음).

**D07 탐색 경로 — 추천:** B+ 트리로 `after_id + 1` 이상의 첫 키를 찾고, 리프 연결을 따라 키마다 줄을 읽어 age를 비교한다. Phase 5의 `range_visit`에 "맞지 않으면 넘기지 않음"만 더한 형태다.

- 범위 안의 줄은 파일에서도 이어져 있으므로, 실제로는 시작 위치에서 한 번 이동한 뒤 읽기 버퍼로 순서대로 읽는다(Phase 3 P3-04와 같은 성질).
- 다른 선택: 파일 처음부터 선형 탐색(`table_scan`)하며 `id ≤ after_id`를 건너뛴다. 커서 앞의 행까지 읽게 되어 뒤쪽 페이지일수록 비싸진다. OFFSET 방식의 비용을 다시 만드는 셈이라 기준선으로 맞지 않다.
- 필터가 있으면 N+1을 키로만 판단할 수 없다. `limit + 1`번째로 **맞는** 행이 어디 있는지 모르기 때문이다. 그래서 그 행을 찾을 때까지 줄을 읽는다. 이것이 T가 생기는 이유다.

### 계측 (D08~D10)

**D08 값 — 추천:** spec "계측 정의"의 R·E·T.

- E에 N+1 확인용 탐색을 넣는다(사용자 확정). T를 따로 두는 이유는, 사용자가 보려는 비용 두 가지가 E 하나에 섞이기 때문이다.
  - 페이지를 **채우는** 비용 = E − T
  - 다음 페이지가 있는지 **확인하는** 비용 = T
  - 긴 불일치 꼬리 시나리오의 마지막 페이지는 거의 전부가 T다.
- 순회 전체로 보면, `has_more: true`인 페이지의 T는 다음 페이지가 다시 검사한다. 그래서 순회 전체의 E 합계 − 검사한 서로 다른 행 수 = 재검사량이다. 기준선 실험에서 순회까지 재지는 않지만(D12), 정의는 이렇게 둔다.
- 다른 선택: E만 둔다(정의가 가장 단순하지만 마지막 페이지 비용이 "채우기"인지 "확인"인지 숫자로 나누지 못한다). 읽은 바이트를 더한다(행 하나가 줄 하나라 정보가 거의 늘지 않는다).

**D09 노출 — 추천:** `/users`의 200 응답에 헤더 `X-Rows-Examined`, `X-Rows-Examined-After-Last`, `X-Engine-Us`를 붙이고, 요청 로그 줄에도 같은 값을 적는다. 필터 없는 요청에도 붙인다.

| 이유 | 다른 선택 |
|---|---|
| 요청마다 측정 도구가 바로 읽을 수 있고, 서버 테스트에서 값을 확인할 수 있다. 본문을 바꾸지 않으므로 Phase 5 클라이언트와 페이지 상한 계산(본문 크기)이 그대로다. 필터 없는 요청에도 붙이면 같은 limit의 "필터 없음" 값(E = R)이 비교 기준이 된다. 발표 자료에서 "MySQL 슬로 로그의 Rows_examined"처럼 설명하기 좋다 | (가) 로그에만 적는다. 클라이언트 API는 그대로지만, 측정 도구가 로그 줄을 요청과 짝지어야 한다. (나) 본문에 `"stats":{…}`를 넣는다. 보기 쉽지만 응답 형식과 고정 부분 크기(D08 페이지 상한)가 바뀐다. (다) 필터가 있을 때만 헤더를 붙인다. 필터 없는 응답은 헤더까지 Phase 5와 같지만 비교 기준을 따로 재야 한다 |

- 헤더 이름은 `X-` 접두사를 쓴다. 표준 헤더가 아니라는 것을 드러내기 위해서다.
- 테스트 빌드와 일반 빌드 모두에 있다. 100만 행 측정은 일반 빌드 서버로 하기 때문이다.

**D10 시간 — 추천:** 엔진 시간은 서버가 `db_page` 호출 앞뒤에서 단조 시계로 잰다(마이크로초 정수). 응답 시간은 측정 도구가 Phase 5와 같은 방법으로 잰다.

| 이유 | 다른 선택 |
|---|---|
| 서버 코드만 바뀌고 Storage에 시계를 넣지 않는다(Windows CLI와 공유하는 코드). 엔진 시간에 들어가는 것(잠금 대기, 맞는 행 최대 `L`개의 JSON 추가)은 spec에 적고, JSON 추가의 몫은 같은 `L`의 필터 없는 페이지 엔진 시간으로 위에서 막는다(그보다 클 수 없음). 변경 없는 데이터라 잠금 대기는 거의 0이다 | (가) `table_page` 안에서 잠금을 잡은 뒤부터 잰다. 잠금 대기가 빠지지만 Storage에 시계가 들어간다. (나) 엔진이 행을 배열에 모으고 JSON은 잠금 밖에서 만든다. 탐색만 순수하게 재지만 메모리 사용과 응답 경로가 바뀐다. 기준선을 재려고 구조를 바꾸는 셈이다 |

### 대표 실험 (D11, D12)

사용자 지시(2026-11-18)로 **age 조건이 드문 사례 하나**만 잰다. 네 가지 분포 전체 실험은 하지 않는다.

**D11 데이터 — 추천:** 100만 행, age 25인 행 1,000개(0.1%)를 id ≡ 1 (mod 1000)에 고르게 둔다(1, 1001, …, 999001). 나머지 age는 20 + (i mod 50)?? ???, 25? ??? 70?? ???. 이름은 Phase 5 도구와 같은 `userNNNNNN`.

| 이유 | 다른 선택 |
|---|---|
| `limit 100`의 첫 페이지가 `has_more: true`가 된다. 그래서 두 경로의 N+1 확인 방식 차이가 보인다. 선형 탐색은 101번째로 맞는 행(100001번째 줄)을 찾을 때까지 **파일 행**을 읽고(T = 1,000), 인덱스는 **인덱스 항목** 하나(K의 101번째)로 판단하고 그 행을 읽지 않는다 | 0.01%(100행). 첫 페이지가 전체 결과라 선형 탐색이 100만 행 전부를 읽어 차이가 더 크게 보인다. 하지만 `has_more: false`라 N+1을 인덱스 항목으로 확인하는 장면이 없다. 차이가 크게 보이는 쪽을 일부러 고르지 않는다 |

기대값(계산, 스크립트로 확인): 두 경로 모두 R = 100, 반환 id 1~99001, `has_more: true`, `next_cursor: 99001`. 선형 E = 100,001, T = 1,000. 인덱스 E = 100, T = 0, K = 101.

**D12 요청·반복 — 추천:**

| 항목 | 값 |
|---|---|
| 요청 | `GET /users?age=25&after_id=0&limit=100` |
| 서버 | 같은 실행 파일·데이터 디렉터리·기본 설정. `--age-path`만 다르다(D17). 경로마다 서버를 새로 띄운다 |
| 워밍업 | 서버마다 같은 요청 5회(측정에서 뺌). 시작 전에 파일을 페이지 캐시에 올린다 |
| 반복 | 30회씩, scan → index → index → scan 순서로 4회 실행. 순서에 따른 환경 변화가 보이도록 실행별 중앙값도 남긴다 |
| 기록 | 클라이언트 응답 시간 중앙값·p90, 엔진 시간 중앙값(참고), 응답 바이트, 헤더 E·T·K, 두 경로 본문의 바이트 비교, 환경(Docker·CPU·커널), 데이터 위치(컨테이너 안 `/tmp`), 커밋 |

- P6-03(기준선)에서는 인덱스가 없으므로 선형 탐색만 같은 방식으로 잰다. 그 기록은 개선 전 커밋의 값으로 남긴다.
- 측정 도구는 헤더 값이 기대값과 다르거나 두 경로의 본문이 다르면 실패로 끝난다.
- benchmark.md에는 관찰값을 적고, 해석은 관찰값과 추정을 나눠 적는다.

### age 보조 인덱스 (D14~D17)

**D14 구조 — 추천: age 값마다 id 오름차순 배열** (`int64_t *ids[151]`, 배열마다 길이·용량)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(가) age별 id 배열** (추천) | age는 0~150의 작은 정수라 배열 151개면 된다. id는 증가 순서로만 부여되므로 INSERT는 해당 배열 끝에 붙이면 정렬이 유지된다. 커서 뒤 시작 위치는 이진 탐색, 그 뒤는 연속 메모리를 차례로 읽는다. 중복 age는 같은 배열의 여러 id로 자연히 다뤄진다. 행당 8바이트 | 중간 삭제는 O(n)이다. 다만 이 DB는 UPDATE·DELETE마다 파일을 다시 쓰며 인덱스도 새로 만드므로 중간 삭제가 필요 없다. age 범위가 작다는 성질에 기댄다. name처럼 값 종류가 많은 컬럼에는 그대로 쓸 수 없다 |
| (나) age별 B+ 트리 151개 (기존 `bptree` 재사용, 키 = id) | 검증된 트리 코드를 쓴다. 범위 탐색(`bpt_range`)·조기 종료 구조가 Phase 5와 같다 | 트리 151개의 노드 오버헤드가 크다(빈 트리도 노드 하나). 트리에 삭제 연산이 없어 결국 다시 쓰기 때 새로 만든다. 이 DB에서는 배열보다 나은 점이 거의 없다 |
| (다) (age, id) 복합 키 B+ 트리 하나 | 일반적인 DB의 보조 인덱스와 같은 모양이라 설명하기 좋다. 값 종류가 많은 컬럼으로 넓히기 쉽다 | 지금 트리는 키가 `int64_t` 하나다. (age, id)를 한 정수에 넣으려면 id 범위를 줄여야 한다(예: 55비트). 아니면 트리의 키 비교를 일반화해야 한다. 이번 범위에 비해 변경이 크다 |

**D15 행 연결 — 추천: age 인덱스에는 id만 두고, 줄 위치는 기존 id 인덱스(`bpt_search`)로 찾는다.**

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(가) id만 저장 → id 인덱스로 위치** (추천) | 줄 위치의 주인이 id 인덱스 하나다. 다시 쓰기로 위치가 모두 바뀌어도 age 인덱스는 id만 맞으면 된다 | 행마다 트리 탐색(100만 행에서 높이 4)이 한 번 더 있다. 한 페이지 최대 1000행이라 작을 것으로 예상하지만 재지는 않는다 |
| (나) (id, 위치)를 함께 저장 | 트리 탐색 없이 바로 읽는다 | 줄 위치의 사본이 두 벌이다. 다시 쓰기마다 두 곳을 맞춰야 하고, 어긋나면 엉뚱한 줄을 읽는다(읽은 줄의 id 재확인으로 드러나긴 한다) |

- 어느 쪽이든 반환할 행이 연속된 줄이 아니므로(드문 조건) 행마다 읽기 위치를 옮긴다.
- 어느 쪽이든 읽은 줄의 **id와 age를 다시 확인**한다. 다르면 500 `STORAGE`(spec "데이터와 인덱스의 일치").

**D16 유지 — 추천: 다시 쓰기 때 새로 만들기**

| 작업 | 처리 | 실패할 때 |
|---|---|---|
| INSERT (`table_append`) | 파일 기록과 id 인덱스 등록 뒤 `ids[age]` 끝에 id 추가 | 메모리 부족이면 id 인덱스 등록 실패와 같은 `DBE_INDEX_FAILED`. 지금처럼 엔진이 중단 상태가 되고, 재시작 때 파일에서 다시 만든다 |
| UPDATE·DELETE (`table_rewrite`) | 새 파일을 쓰며 새 id 인덱스를 만드는 같은 반복에서 새 age 인덱스도 만든다. 바꿔치기가 성공하면 둘을 **함께** 교체 | 다시 쓰기가 실패하면 새 age 인덱스도 버리고 옛것을 그대로 둔다(id 인덱스와 같은 규칙) |
| 재시작 (`table_open`) | 시작 탐색에서 id 인덱스와 함께 만든다 | 메모리 부족이면 열기 실패(지금과 같음) |
| 검증 | 테스트 빌드 `table_test_validate_age_index`: 파일 전체를 읽어 age별 id 목록을 만들고 인덱스와 비교 | |

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(가) 다시 쓰기 때 새로 만들기** (추천) | 이 DB의 UPDATE·DELETE는 이미 파일과 id 인덱스를 통째로 새로 만든다. 같은 반복에 얹으면 된다. 갱신 로직(삭제·이동)이 없어 틀릴 곳이 적고, 실패 시 옛 상태로 남는 규칙도 그대로 따른다 | 한 행만 바꿔도 age 인덱스 전체를 다시 만든다(지금도 파일 전체를 다시 쓰므로 비용의 차수는 같다). 쓰기 시간이 늘지만 이번에 재지 않는다 |
| (나) 바뀐 행만 갱신 | 쓰기마다 할 일이 작다 | 배열 중간 삭제·이동, age가 바뀐 행을 옛 배열에서 빼고 새 배열에 정렬을 유지하며 넣는 작업이 필요하다. 파일은 통째로 다시 쓰는데 인덱스만 부분 갱신하면 실패 시 되돌리기가 복잡해진다 |

**D16 계측 추가:** 헤더 `X-Age-Index-Keys`(K)와 `X-Access-Path`(`id`·`scan`·`age-index`). 정의는 spec "age 보조 인덱스 → 계측".

**D17 비교용 경로 선택 — 추천: 서버 시작 옵션 `--age-path scan|index`(기본 `index`).** 인덱스는 옵션과 상관없이 항상 유지하고, 옵션은 읽기 경로만 고른다. 엔진에서는 `PageFilter`의 경로 필드로 고르고, 단위 테스트는 같은 Table에서 두 경로를 번갈아 불러 결과를 비교한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(가) 서버 시작 옵션** (추천) | API(요청 파라미터)가 바뀌지 않는다. 실행 파일·데이터·설정이 같고 옵션 하나만 다르다. 응답 헤더 `X-Access-Path`로 어느 경로가 실행됐는지 확인할 수 있다 | 경로를 바꾸려면 서버를 다시 띄워야 한다. 측정 순서를 바꿔 두 번 돌려 환경 변화를 본다 |
| (나) 요청 파라미터(`?path=scan`) | 같은 서버에서 요청마다 번갈아 잴 수 있어 환경 차이가 가장 작다 | 클라이언트 API에 내부 실행 방식이 드러나고, Phase 5의 "모르는 파라미터는 거부" 계약에 예외가 생긴다 |
| (다) 개선 전 커밋과 개선 후 커밋의 실행 파일 비교 | "개선 전/후 커밋"이 그대로 실험 대상이다 | 두 실행 파일은 인덱스 유지 코드 등 다른 부분도 다르다. 같은 코드에서 경로만 바꾸는 쪽이 비교가 깨끗하다. 대신 P6-03의 기준선 기록(개선 전 커밋)과 P6-05의 scan 경로 값을 나란히 적어, 크게 다르지 않은지 본다 |

- 인덱스를 항상 유지하므로 `scan` 경로로 띄워도 메모리·쓰기 비용은 같다. 그래서 이 옵션으로는 쓰기 비용·메모리를 비교할 수 없다. 이번에 재지 않는 범위다.
- 인덱스 경로의 N+1은 age 배열의 다음 항목이 있는지로 판단한다. 페이지 하나는 공유 잠금 안에서 읽으므로 그 사이 인덱스와 파일이 바뀌지 않는다.

## 요청 흐름

```text
GET /users?age=30&after_id=200&limit=100
  → 파라미터 검증 (실패 → 400 INVALID_PARAM, 엔진 안 부름)
  → t0 = 시계
  → db_page(after_id, limit, {age 30})              [공유 잠금]
       → table_page: B+ 트리로 201 이상 첫 키
       → 키마다 줄을 읽고 E++ → age가 30이면
            맞는 수 < limit  → fn(행) (JSON 추가), R++
            맞는 수 = limit  → has_more = 1, 멈춤 (이 행은 넘기지 않음)
         마지막 반환 뒤의 줄은 T에도 센다
  → 엔진 시간 = 시계 − t0
  → 본문 {"ok":true,...,"has_more":..,"next_cursor":..}
  → 헤더 X-Rows-Examined / X-Rows-Examined-After-Last / X-Engine-Us
  → 전송 (잠금 밖), 로그 한 줄
```
