## 측정 방법과 읽는 법

**환경**
- Windows 10 위 Docker Desktop(WSL2) 안의 `gcc:13` 컨테이너, CPU 8개. 2026-11-17 측정.
- **클라이언트와 서버가 같은 컨테이너에서 CPU 8개를 나눠 쓴다.** 워커를 CPU 수 가까이 늘리면 클라이언트와 CPU를 다툰다. 같은 설정도 회차마다 흔들린다(표의 "3회 범위"). 숫자는 이 환경 안에서의 **상대 비교**로 읽는다.

**도구**
- 부하 생성기 `tools/loadgen.c`(C, 클라이언트마다 스레드 하나)가 요청을 보내고, `tools/load.py`는 서버 띄우기·설정 바꾸기·표 만들기만 한다.
- **닫힌 고리:** 클라이언트는 응답을 받자마자 다음 요청을 보낸다. 그래서 서버가 느려지면 새 요청도 줄어든다. 외부에서 일정한 비율로 계속 들어오는 부하(열린 고리)는 재지 않았다.

**무엇을 "성공"으로 세나**
- 성공 = 상태 `200`이고, 헤더 끝(빈 줄)과 `Content-Length`를 받은 뒤 그 길이만큼의 본문을 **끝까지** 받은 응답. JSON 내용까지 검사하지는 않는다(내용의 정확성은 서버 테스트가 맡는다).
- 덜 받은 채 끊기거나(EOF·연결 재설정) 30초 기한을 넘기면 "불완전", 연결·전송 실패는 "실패"로 따로 센다. 이번 측정에서 불완전·실패는 **모두 0건**이었다.

**처리량과 응답 시간**
- 측정 구간은 2초. **구간 안에서 완료된** 요청만 센다. 처리량 = 구간 안 성공 수 / 2초.
- 구간이 끝나면 새 요청을 보내지 않는다. 그때 진행 중이던 요청은 끝까지 받지만(드레인) 집계하지 않고 "늦음(제외)"으로만 적는다. 드레인 시간은 분모에 넣지 않는다. 표의 "늦음"이 클라이언트 수와 같은 것은 구간이 끝나는 순간 클라이언트마다 요청이 하나씩 진행 중이었기 때문이다.
- p50·p95·p99는 **구간 안에서 완료된 성공 요청만**의 응답 시간이다(연결 → 요청 보내기 → 응답 끝까지 받기, 큐 대기 포함). 503·불완전·늦음 요청의 시간은 들어가지 않으므로 전체 사용자 경험을 다 나타내지는 않는다.
- 응답 시간을 클라이언트에서 재는 이유: 서버 로그의 시간(연결을 꺼낸 뒤 처리 시간)에는 큐 대기가 보이지 않는다(walkthrough 6장에서 P3-02 서버가 로그에는 0.10 ms, 클라이언트에는 3,366 ms였던 것).
- 설정마다 같은 서버에 2초씩 3번 재고, 처리량이 가운데인 회차의 값을 적는다.

**연결 정리 (정상 클라이언트와 다른 조건)**
- 부하 생성기는 응답을 끝까지 받은 뒤 연결을 재설정(RST, `SO_LINGER` 0)으로 닫는다. 이유는 아래 5-(2). RST 종료는 TCP 연결 정리와 커널 부하를 바꾸므로, 정상 FIN 종료 클라이언트(`curl` 등)의 처리량과 같다고 보지 않는다.

**요청**
- 선형 탐색 `SELECT * FROM users WHERE age = 150;`(결과 약 6,600행), id 조회는 1..1,000,000 중 무작위, 섞기는 id 조회 80% · id 범위(21행) 10% · INSERT 10%.

## 1. Phase 2와 비교: 떠 있는 프로세스의 이득

| 방식 | id 하나 조회에 걸린 시간 |
|---|---|
| CLI 한 번 실행 (`minidb q.sql`, 파일 전체 읽기·인덱스 구축 포함, 3회 중앙값) | 346 ms |
| 떠 있는 서버에 HTTP 요청 (클라이언트 1개, 2초 동안 9,152회) | **중앙값 0.18 ms**, p99 0.67 ms |
| (참고) 서버 시작 비용: 같은 파일 읽기·인덱스 구축, 한 번만 | 127 ms |

Phase 2는 "CLI 한 번 실행 기준으로는 인덱스 조회와 선형 탐색의 차이가 2배 미만"이라고 결론 냈다([phase2/benchmark.md](../phase2/benchmark.md)). 실행할 때마다 파일 전체를 읽어 인덱스를 다시 만드는 비용이 조회 자체보다 훨씬 컸기 때문이다. 서버는 그 비용을 시작할 때 **한 번만** 낸다. 그 뒤 id 조회 한 건은 HTTP 연결·JSON까지 포함해도 0.18 ms다. CLI 한 번 실행보다 세 자릿수 작다. 메모리 인덱스의 이득이 서버 구조에서 비로소 드러난다.

(CLI 346 ms와 서버 시작 127 ms는 같은 일을 하는데도 차이가 크다. CLI 쪽 3회 값이 흔들렸고, 따로 원인을 재지는 않았다. 결론은 어느 값을 써도 같다.)

## 2. 워커 수: id 조회만, 클라이언트 16개

| 설정 | 처리량 (성공/초) | 3회 범위 | p50 ms | p95 ms | p99 ms | 최대 ms |
|---|---|---|---|---|---|---|
| 워커 1개 | 7,434 | 7,414 ~ 9,262 | 1.85 | 3.87 | 5.42 | 27.5 |
| 워커 2개 | 16,952 | 15,897 ~ 17,370 | 0.84 | 1.51 | 2.06 | 3.94 |
| 워커 4개 | 18,466 | 16,774 ~ 24,212 | 0.62 | 1.87 | 4.81 | 45.8 |
| 워커 8개 | 30,109 | 23,650 ~ 32,638 | 0.41 | 1.10 | 2.27 | 23.1 |

- 워커를 늘리면 처리량이 늘고 p50이 줄어든다(워커 1개 → 8개: 약 4배, p50 1.85 → 0.41 ms).
- 늘어나는 폭은 고르지 않다(2 → 4개는 거의 그대로, 4 → 8개는 크게). 3회 범위가 넓어 이 환경의 흔들림(클라이언트와 CPU를 나눠 씀)이 큰 영향을 준다. 단조 증가와 대략의 배수만 읽는다.
- 클라이언트 16개가 워커 1개에 몰리면 각자 큐에서 기다리므로 p50이 1.85 ms다. 처리 한 건은 클라이언트 1개일 때 0.18 ms였다(1).
- 왜 겹쳐 돌 수 있는지는 짐작만 한다. id 조회는 엔진 잠금 안의 일(트리 탐색, 한 줄 `pread`, 행 하나를 JSON으로 쓰는 콜백)이 짧고, 연결 맺기·요청 읽기·응답 보내기는 잠금 밖이다. 잠금 안팎의 시간을 따로 재지는 않았다.

## 4. 큐 크기: 워커 1개, 클라이언트 16개, id 조회만

| 설정 | 처리량 (성공/초) | 3회 범위 | p50 ms | p95 ms | p99 ms | 503 (2초 동안) |
|---|---|---|---|---|---|---|
| 큐 1칸 | 7,740 | 7,640 ~ 8,142 | 0.65 | 1.46 | 2.48 | **32,893** |
| 큐 64칸 | 9,148 | 8,588 ~ 9,500 | 1.59 | 2.69 | 3.20 | 0 |

- 동시에 16개가 몰리면 큐 1칸은 자리가 금방 차서, 2초 동안 32,893번 503 `BUSY`를 돌려줬다(성공 약 15,000건보다 많다). 503은 기다리지 않고 바로 돌아오므로 클라이언트가 곧장 다시 보내 503이 또 쌓인다.
- 큐 64칸에서는 16개가 모두 앉을 수 있어 503이 없다. 대신 큐에서 기다린 만큼 성공 요청의 p50이 0.65 ms에서 1.59 ms로 늘었다. 거절 대신 기다림이다. (큐 1칸의 p50이 낮은 것은 기다려야 했을 요청이 503으로 빠져 백분위에서 제외됐기 때문이기도 하다.)
- 큐 크기는 "잠깐 몰릴 때 거절할지, 줄 세울지"를 정한다.

## 5. 환경이 만든 병목 두 가지 (측정 중 발견)

**(1) 로그·데이터를 Windows와 공유하는 폴더에 두면** (워커 4개, 클라이언트 16개, id 조회만)

| 설정 | 처리량 (성공/초) | 3회 범위 | p50 ms | p95 ms | p99 ms |
|---|---|---|---|---|---|
| 컨테이너 안 임시 폴더 (`/tmp`) | 25,136 | 23,260 ~ 25,160 | 0.55 | 1.11 | 1.79 |
| 호스트 공유 폴더 (Docker 바인드 마운트) | **1,244** | 1,192 ~ 1,425 | 13.3 | 16.0 | 17.5 |

처음 측정은 데이터와 서버 로그(stderr를 리디렉션한 파일)를 프로젝트 폴더(`/src/build`, Windows와 공유)에 뒀다. 그랬더니 워커 수·잠금 방식과 상관없이 처리량이 약 1,000건/초 근처에 머물렀다. 서버는 요청마다 로그 한 줄을 stderr에 쓰고, stderr 쓰기는 한 번에 하나씩만 된다. 공유 폴더에 쓰는 시간이 길어 워커들이 로그 쓰기 앞에서 줄을 선 것으로 본다. 쓰기 한 번의 시간을 직접 재지는 않았다. 데이터 파일 읽기(`pread`)도 같은 공유 폴더라 함께 느려졌을 수 있다. 확실한 것은 위치만 바꿨을 때 처리량이 약 20배 차이 난다는 관찰이다. 잠금을 잘게 나눠도, 요청마다 지나가는 다른 공유 자원이 느리면 그것이 상한이 된다. 측정 도구는 이제 컨테이너 안 임시 폴더를 쓴다.

같은 이유로 P3-04 때 잰 `make read-bench` 값(선형 탐색 4개 동시 813 → 313 ms)도 공유 폴더 조건의 숫자였다. 임시 폴더로 다시 잰 값은 아래 6에 있다.

**(2) TIME_WAIT 연결이 쌓이면**

이 서버는 keep-alive를 지원하지 않아 요청마다 연결을 새로 맺고, 응답을 보낸 뒤 **서버가 먼저 닫는다**. 일반적인 정상 종료에서는 먼저 닫은 쪽에 TIME_WAIT 연결이 남는다. 이 환경(Linux 컨테이너)에서는 60초 남았고, 수는 32,768에서 더 늘지 않았다. 둘 다 이 환경에서 관찰한 값이며 모든 운영체제의 고정값은 아니다. 같은 설정(워커 4개, 클라이언트 16개, 5초)을 연달아 4번 재 보니, TIME_WAIT 수가 0 → 14,106 → 28,211 → 32,768로 늘었고, 32,768에 닿은 뒤로는 처리량이 절반 가까이 떨어졌다(5초 동안 성공 85,551 → 41,445건, 고치기 전 도구로 잰 값). 측정 순서에 따라 같은 설정이 2배 넘게 다르게 나온 원인이었다.

그래서 부하 생성기는 응답을 끝까지 받은 뒤 RST로 닫는다(위 "연결 정리"). 실제 서비스라면 keep-alive로 연결을 다시 쓰거나(Phase 3 제외 항목), 클라이언트가 먼저 닫게 하는 방법을 쓴다.

## 6. 읽기 병렬화 다시 재기 (`make read-bench`, 임시 폴더)

`tools/read_parallel.py`. 이 도구도 응답 본문을 `Content-Length`만큼 끝까지 받았는지 확인하도록 고쳤다(불완전하면 측정을 멈춘다). 탐색 묶음의 시간은 마지막 응답까지 걸린 전체 시간이다. 3회 중앙값.

| 항목 (클라이언트·워커 4개) | 전역 잠금 (P3-03까지) | 읽기·쓰기 잠금 (P3-04) |
|---|---|---|
| 선형 탐색 1개 응답 | 78 ms | 77 ms |
| 선형 탐색 4개 동시, 전체 시간 | 304 ms (1개의 3.9배) | **88 ms** (1.1배) |
| INSERT 응답 (부하 없음) | 0.36 ms | 0.29 ms |
| INSERT 응답 (선형 탐색 4개가 계속 도는 중), 중앙값 / 최대 | 180 ms / 2,869 ms | **77 ms / 114 ms** |

| 항목 (클라이언트·워커 16개) | 전역 잠금 | 읽기·쓰기 잠금 |
|---|---|---|
| 선형 탐색 16개 동시, 전체 시간 | 1,189 ms (1개의 9.6배) | **274 ms** (3.7배) |
| INSERT 응답 (선형 탐색 16개가 계속 도는 중), 중앙값 / 최대 | 1,038 ms / 2,095 ms | **116 ms / 142 ms** |

- 전역 잠금에서는 4개가 1개의 약 4배(한 줄로 섬), 읽기·쓰기 잠금에서는 거의 1개 시간(1.1배)에 끝났다. 16개에서는 읽기·쓰기 잠금도 3.7배가 걸렸다. 동시에 실행돼도 CPU 8개를 16개 요청과 클라이언트가 나눠 쓰기 때문으로 본다.
- 쓰기 우선 정책은 대기 중인 INSERT 뒤로 새 SELECT를 세워, 읽기가 계속 앞지르는 것을 막는다. 그래서 탐색이 계속 도는 동안의 INSERT가 전역 잠금보다 짧았다. 다만 최대 114 ms는 이 실험의 관찰값이고, 탐색 1개(77 ms)보다도 길다. 다른 INSERT·스케줄링·통신 비용이 더해질 수 있어 **INSERT 응답 시간의 상한을 보장하지 않는다.**

## 정리

| 질문 | 측정이 보여 준 것 |
|---|---|
| 서버 구조는 무엇을 바꿨나 | 시작 비용(파일 전체 읽기·인덱스 구축)을 한 번만 낸다. id 조회 한 건이 CLI 한 번 실행 수백 ms → 서버 0.18 ms |
| 워커(스레드 풀)는 무엇을 바꿨나 | 요청 처리가 겹쳐 돈다. id 조회 처리량이 워커 1 → 8개에서 약 4배. 느린 클라이언트가 서버 전체를 막지 않는다(walkthrough 6장) |
| 읽기·쓰기 잠금은 무엇을 바꿨나 | 잠금 안에 오래 머무는 문장(선형 탐색)이 서로 기다리지 않는다. 처리량 약 3배, p99 2,000 → 109 ms. id 조회는 약 1.5배, INSERT가 섞이면 차이가 줄어든다 |
| 큐 크기는 무엇을 바꿨나 | 잠깐 몰릴 때 거절(503)할지 기다리게 할지. 큐 1칸은 2초 동안 503 3만여 번, 64칸은 0번 대신 성공 요청의 p50이 약 2.4배 |
| 잠금 말고 병목이 될 수 있는 것 | 요청마다 지나가는 다른 공유 자원: 느린 공유 폴더(처리량 약 1/20), 쌓인 TIME_WAIT 연결(처리량 약 1/2) |
