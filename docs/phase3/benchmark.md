# Phase 3 부하 측정 (P3-05)

API 서버를 같은 데이터(100만 행)로 여러 설정으로 띄우고, 클라이언트 여러 개가 쉬지 않고 요청을 보냈을 때의 처리량과 응답 시간을 쟀다. 판정(통과·실패)에 쓰는 측정이 아니라, 설계 결정이 실제로 어떤 차이를 만드는지 보는 기록이다.

```bash
docker run --rm -v "$PWD:/src" -w /src gcc:13 make load-bench   # 아래 1~5 (약 2분)
docker run --rm -v "$PWD:/src" -w /src gcc:13 make read-bench   # 아래 6 (약 1분)
```

## 측정 환경과 읽는 법

- Windows 10 위 Docker Desktop(WSL2) 안의 `gcc:13` 컨테이너, CPU 8개. 2026-11-17 측정.
- **클라이언트와 서버가 같은 컨테이너에서 CPU 8개를 나눠 쓴다.** 그래서 워커를 CPU 수 가까이 늘리면 클라이언트와 CPU를 다툰다. 숫자는 이 환경 안에서의 **상대 비교**로 읽는다.
- 부하 생성기 `tools/loadgen.c`(C, 클라이언트마다 스레드 하나)가 요청을 보내고, `tools/load.py`는 서버 띄우기·설정 바꾸기·표 만들기만 한다. 클라이언트는 응답을 받자마자 다음 요청을 보낸다(닫힌 고리).
- **응답 시간은 클라이언트에서 잰다**: 연결 → 요청 보내기 → 응답 끝까지 받기. 큐에서 기다린 시간이 들어간다. 서버 로그의 시간(꺼낸 뒤 처리 시간)에는 이 대기가 보이지 않는다(walkthrough 6장 실습에서 P3-02 서버가 로그에는 0.10 ms, 클라이언트에는 3,366 ms였던 것).
- 설정마다 2초씩 3번 재고 처리량이 가운데인 회차를 적는다. "3회 범위"는 가장 낮은 처리량과 가장 높은 처리량이다.
- 선형 탐색은 `SELECT * FROM users WHERE age = 150;`(결과 약 6,600행), id 조회는 1..1,000,000 중 무작위, 섞기는 id 조회 80% · id 범위(21행) 10% · INSERT 10%.

## 1. Phase 2와 비교: 떠 있는 프로세스의 이득

| 방식 | id 하나 조회에 걸린 시간 |
|---|---|
| CLI 한 번 실행 (`minidb q.sql`, 파일 전체 읽기·인덱스 구축 포함, 3회 중앙값) | 189 ms |
| 떠 있는 서버에 HTTP 요청 (클라이언트 1개, 2초 동안 6,995회) | **중앙값 0.23 ms**, p99 0.94 ms |
| (참고) 서버 시작 비용: 같은 파일 읽기·인덱스 구축, 한 번만 | 260 ms |

Phase 2는 "CLI 한 번 실행 기준으로는 인덱스 조회와 선형 탐색의 차이가 2배 미만"이라고 결론 냈다([phase2/benchmark.md](../phase2/benchmark.md)). 실행할 때마다 파일 전체를 읽어 인덱스를 다시 만드는 비용이 조회 자체보다 훨씬 컸기 때문이다. 서버는 그 비용을 시작할 때 **한 번만** 낸다. 그 뒤 id 조회 한 건은 HTTP 연결·JSON까지 포함해도 0.23 ms다. CLI 한 번(189 ms)의 약 800분의 1이다. 메모리 인덱스의 이득이 서버 구조에서 비로소 드러난다.

## 2. 워커 수: id 조회만, 클라이언트 16개

| 설정 | 처리량 (성공/초) | 3회 범위 | p50 ms | p95 ms | p99 ms | 최대 ms |
|---|---|---|---|---|---|---|
| 워커 1개 | 5,966 | 4,518 ~ 6,814 | 2.31 | 4.64 | 7.81 | 29.7 |
| 워커 2개 | 11,956 | 10,184 ~ 12,004 | 1.19 | 2.17 | 3.13 | 6.10 |
| 워커 4개 | 20,311 | 20,026 ~ 20,422 | 0.69 | 1.35 | 2.19 | 6.01 |
| 워커 8개 | 22,733 | 19,048 ~ 25,268 | 0.54 | 1.61 | 2.92 | 14.7 |

- 워커 1 → 2 → 4개에서 처리량이 거의 2배씩 는다. id 조회는 엔진 안의 시간이 아주 짧고(트리 탐색 + 한 줄 `pread`), 대부분의 시간이 연결 맺기·요청 읽기·응답 쓰기 같은 네트워크 처리라서 워커끼리 겹쳐 돌 수 있다.
- 워커 8개는 4개보다 조금만 늘고 범위도 넓다. CPU 8개를 클라이언트 스레드 16개와 나눠 쓰기 때문이다.
- 클라이언트 16개가 워커 1개에 몰리면 각자 큐에서 기다리므로 p50이 2.31 ms다(처리 자체는 0.2 ms 수준). 워커를 늘리면 기다림이 줄어 p50이 내려간다.

## 3. 요청 종류 × 잠금 방식: 워커 4개, 클라이언트 8개

| 설정 | 처리량 (성공/초) | 3회 범위 | p50 ms | p95 ms | p99 ms | 최대 ms |
|---|---|---|---|---|---|---|
| id 조회만 — 전역 잠금 | 17,070 | 16,254 ~ 18,800 | 0.38 | 0.93 | 1.84 | 5.39 |
| id 조회만 — 읽기·쓰기 잠금 | 21,286 | 21,156 ~ 21,536 | 0.33 | 0.66 | 1.14 | 5.59 |
| 섞기 — 전역 잠금 | 17,992 | 14,720 ~ 19,353 | 0.38 | 0.83 | 1.49 | 4.45 |
| 섞기 — 읽기·쓰기 잠금 | 19,495 | 18,866 ~ 20,003 | 0.35 | 0.74 | 1.31 | 11.0 |
| 선형 탐색만 — 전역 잠금 (클라이언트 4개) | 15 | 15 ~ 15 | 226 | 260 | 2,284 | 2,284 |
| 선형 탐색만 — 읽기·쓰기 잠금 (클라이언트 4개) | **46** | 46 ~ 47 | **87** | 103 | 106 | 108 |

- **잠금 방식의 차이는 문장이 잠금 안에서 오래 머물 때 크다.** 선형 탐색(잠금 안 약 80 ms)은 읽기·쓰기 잠금에서 처리량이 3배이고, p99가 2,284 ms에서 106 ms로 줄었다. 전역 잠금에서는 탐색이 한 줄로 서서, 운이 나쁜 요청은 앞의 탐색 여러 개를 기다린다.
- id 조회는 잠금 안의 시간이 마이크로초 단위라 차이가 작다(약 25%). 시간 대부분이 잠금 밖(네트워크·HTTP·JSON)이고, 그 부분은 P3-03의 스레드 풀이 이미 겹쳐 돌린다.
- 섞기(INSERT 10%)는 두 방식이 비슷하다. INSERT는 어느 쪽이든 배타 잠금이고, 읽기 쪽 이득은 id 조회처럼 작다.

## 4. 큐 크기: 워커 1개, 클라이언트 16개, id 조회만

| 설정 | 처리량 (성공/초) | 3회 범위 | p50 ms | p95 ms | p99 ms | 503 (2초 동안) |
|---|---|---|---|---|---|---|
| 큐 1칸 | 5,650 | 5,377 ~ 5,922 | 0.80 | 1.55 | 2.25 | **33,371** |
| 큐 64칸 | 7,074 | 6,314 ~ 7,088 | 2.12 | 3.26 | 4.12 | 0 |

- 동시에 16개가 몰리면 큐 1칸은 자리가 금방 차서, 2초 동안 33,371번 503 `BUSY`를 돌려줬다(성공 약 11,000건보다 많다). 503은 기다리지 않고 바로 돌아오므로 클라이언트가 곧장 다시 보내 503이 또 쌓인다.
- 큐 64칸에서는 16개가 모두 앉을 수 있어 503이 없다. 대신 큐에서 기다린 만큼 p50이 0.80 ms에서 2.12 ms로 늘었다. 거절 대신 기다림이다.
- 큐 크기는 "잠깐 몰릴 때 거절할지, 줄 세울지"를 정한다. 기본값 64는 워커 4개가 1 ms 안팎에 처리하는 요청이 잠깐 몰리는 정도는 흡수하는 크기다.

## 5. 환경이 만든 병목 두 가지 (측정 중 발견)

**(1) 로그·데이터를 Windows와 공유하는 폴더에 두면** (워커 4개, 클라이언트 16개, id 조회만)

| 설정 | 처리량 (성공/초) | 3회 범위 | p50 ms | p95 ms | p99 ms |
|---|---|---|---|---|---|
| 컨테이너 안 임시 폴더 (`/tmp`) | 20,813 | 15,204 ~ 21,079 | 0.67 | 1.28 | 2.11 |
| 호스트 공유 폴더 (Docker 바인드 마운트) | **987** | 946 ~ 1,168 | 14.8 | 28.3 | 37.2 |

처음 측정은 데이터와 서버 로그(stderr를 리디렉션한 파일)를 프로젝트 폴더(`/src/build`, Windows와 공유)에 뒀다. 그랬더니 워커 수·잠금 방식과 상관없이 처리량이 약 1,000건/초에서 멈췄다. 서버는 요청마다 로그 한 줄을 stderr에 쓰는데, 공유 폴더에 쓰기 한 번이 약 1 ms 걸리고, stderr 쓰기는 한 번에 하나씩만 되므로 **모든 워커가 로그 쓰기 앞에서 줄을 섰다**. 잠금을 아무리 잘게 나눠도, 요청마다 지나가는 다른 공유 자원(여기서는 로그 파일)이 느리면 그것이 상한이 된다. 측정 도구는 이제 컨테이너 안 임시 폴더를 쓴다.

같은 이유로 P3-04 때 잰 `make read-bench` 값(선형 탐색 4개 동시 813 → 313 ms)도 공유 폴더에서 파일을 읽어 느려진 숫자였다. 임시 폴더로 다시 잰 값은 아래 6에 있다.

**(2) TIME_WAIT 연결이 쌓이면**

이 서버는 keep-alive를 지원하지 않아 요청마다 연결을 새로 맺고, 응답을 보낸 뒤 **서버가 먼저 닫는다**. 먼저 닫은 쪽에는 연결이 TIME_WAIT 상태로 60초 남는다. 초당 2만 건이면 수 초 만에 수만 개가 쌓인다. 같은 설정(워커 4개, 클라이언트 16개, 5초)을 연달아 4번 재 보니, TIME_WAIT 수가 0 → 14,106 → 28,211 → 32,768(상한)로 늘었고, 상한에 닿은 뒤로는 처리량이 절반 가까이 떨어졌다(5초 동안 성공 85,551 → 41,445건). 측정 순서에 따라 같은 설정이 2배 넘게 다르게 나온 원인이었다.

그래서 부하 생성기는 응답을 끝까지 받은 뒤 연결을 재설정(RST, `SO_LINGER` 0)으로 닫는다. 측정하는 일(연결·요청·응답 받기)은 같고 응답을 다 받은 뒤의 정리만 다르다. 실제 클라이언트(`curl` 등)는 이렇게 닫지 않는다. 실제 서비스라면 keep-alive로 연결을 다시 쓰거나(Phase 3 제외 항목), 클라이언트가 먼저 닫게 하는 방법을 쓴다.

## 6. 읽기 병렬화 다시 재기 (`make read-bench`, 임시 폴더)

선형 탐색 4개 동시, 워커 4개, 3회 중앙값.

| 항목 | 전역 잠금 (P3-03까지) | 읽기·쓰기 잠금 (P3-04) |
|---|---|---|
| 선형 탐색 1개 응답 | 77 ms | 79 ms |
| 선형 탐색 4개 동시, 전체 시간 | 493 ms (1개의 6.4배) | **100 ms** (1.3배) |
| INSERT 응답 (부하 없음) | 0.37 ms | 0.75 ms |
| INSERT 응답 (선형 탐색 4개가 계속 도는 중), 중앙값 / 최대 | 237 ms / 1,406 ms | **71 ms / 99 ms** |

전역 잠금에서는 4개가 1개의 4배보다도 오래 걸렸다(6.4배). 한 줄로 선 것만으로는 4배여야 하는데, 나머지가 어디서 왔는지(잠금을 넘겨받는 비용, CPU를 나눠 쓰는 클라이언트 등)는 따로 재지 않았다. 읽기·쓰기 잠금에서는 4개가 1개와 거의 같은 시간(1.3배)에 끝났다. 쓰기 우선이라 INSERT는 이미 돌던 탐색만 기다리고(최대 99 ms, 탐색 1개 시간 안쪽), 전역 잠금처럼 뒤에 온 탐색에 밀리지 않는다.

## 정리

| 질문 | 측정이 보여 준 것 |
|---|---|
| 서버 구조는 무엇을 바꿨나 | 시작 비용(파일 전체 읽기·인덱스 구축)을 한 번만 낸다. id 조회 한 건이 CLI 189 ms → 서버 0.23 ms |
| 워커(스레드 풀)는 무엇을 바꿨나 | 네트워크 처리가 겹쳐 돈다. id 조회 처리량이 워커 1 → 4개에서 약 3.4배. 느린 클라이언트가 서버 전체를 막지 않는다(walkthrough 6장) |
| 읽기·쓰기 잠금은 무엇을 바꿨나 | 잠금 안에 오래 머무는 문장(선형 탐색)이 서로 기다리지 않는다. 처리량 3배, p99 2,284 → 106 ms. 짧은 문장(id 조회)은 차이가 작다 |
| 큐 크기는 무엇을 바꿨나 | 잠깐 몰릴 때 거절(503)할지 기다리게 할지. 큐 1칸은 2초 동안 503 3만여 번, 64칸은 0번 대신 p50이 2.6배 |
| 잠금 말고 병목이 될 수 있는 것 | 요청마다 지나가는 다른 공유 자원: 느린 곳에 쓰는 로그(처리량 1/20), 쌓인 TIME_WAIT 연결(처리량 1/2) |
