## 확인이 필요한 새 정책·상한·인터페이스 (요약)

| 항목 | 추천 | 이유 |
|---|---|---|
| 응답 예산 | 요청당 JSON 본문 8 MiB(초기 설정) | 100만 건 중 수십만 행까지 담을 수 있다. 이 값은 **응답 크기** 상한이다. 워커의 실제 메모리는 여기에 요청 본문·문장 목록·버퍼 여유분이 더해지며 P3-05에서 잰다 |
| 행 예산 | 요청당 SELECT 행 합계 100,000 | 오류 메시지로 이해하기 쉬운 기준이다. 실제 보호는 바이트 예산이 맡는다 |
| 초과 처리 | 그 SELECT 결과를 통째로 버리고 앞 결과는 유지, 이후 문장은 실행 안 함 | 잘린 결과를 완전한 결과로 오해하지 않게 한다. SELECT라서 데이터가 바뀌지 않는다 |
| INSERT 자리 선확인 | 결과를 쓸 자리가 없으면 실행하지 않음 | "저장됐는데 응답에서 빠짐"을 예산 때문에 만들지 않는다 |
| 전체 선파싱 | 구문 오류면 0건 실행 | 부분 실행이 생기는 경우를 실행 단계 오류로 줄인다. CLI와 다르다는 점은 문서에 적는다 |
| 오류 코드 `error.code` | 표의 12개 값 | 클라이언트가 문구 대신 코드로 재시도 여부를 판단한다 |
| 중단 상태 | 쓰기 도중 오류·인덱스 등록 실패 시 진입, 사유를 구분 | 파일과 인덱스가 어긋난 채로 계속 답하면 같은 행이 경로에 따라 보이거나 안 보인다. `index_failed`는 파일이 온전하므로 재시작해서 인덱스를 다시 만들면 복구된다(재시작 때 메모리가 충분할 때). `write_failed`는 파일 끝이 깨졌을 수 있어서 재시작이 "데이터 파일 손상"으로 거부될 수 있다. 이때는 운영자가 직접 고쳐야 한다 |
| `stored_id` | 파일 기록 완료(`fprintf`·`fflush` 성공)가 확인된 뒤 실패한 INSERT의 id. 쓰기 도중 오류에는 넣지 않음 | 클라이언트가 그 INSERT를 다시 보내지 않게 한다. 결과를 모르는 경우와 섞지 않는다 |
| 기한 5 / 10 / 10초 | 호출 / 수신 전체 / 전송 전체 | 로컬과 LAN에서 1 MiB 요청이나 8 MiB 응답을 보내기에 충분하고, 느린 연결이 워커를 오래 붙잡지 못하게 한다 |
| 종료 유예 10초 + 문장 경계 | 실행 중인 문장은 끊지 않음. 10초는 절대 상한이 아님 | 쓰기 도중에 끊으면 반쯤 쓰인 줄이 남는다. 대신 종료 완료 시간은 실행 중인 문장의 실행 시간에 달려 있다 |
| CLI 옵션 | `--max-rows`, `--max-response` 추가 | 테스트에서 작은 값으로 경계를 확인할 수 있다 |

## 엔진과 서버의 연결 (DB-P3-D04)

서버는 `main.c`와 나란히 놓이는 또 하나의 프런트엔드다.

```text
CLI     main.c   ─┐                                     ┌─ Executor ─ Storage ─ B+ 트리
                  ├─ Parser(잠금 밖) ─ db_exec(문장마다 잠금) ─┤
서버    server.c ─┘                                     └─ 결과는 ResultSink 콜백으로
```

```c
/* src/db.h */
typedef struct Db Db;   /* Table + 잠금 + 상태(정상 / 중단과 사유). 불투명 타입 */

int  db_open(const char *data_dir, Db **out, DbError *err);
/* 문장 하나를 잠금 안에서 실행한다. sink 콜백도 잠금 안에서 호출되므로 메모리 작업만 해야 한다.
 * 중단 상태면 실행하지 않고 -1(err->kind = DBE_HALTED).
 * INSERT가 파일 기록 완료 뒤 인덱스 등록에 실패하면 *stored_id에 id를 담는다(그 밖에는 0).
 * 쓰기 도중 오류(DBE_WRITE_FAILED)는 기록 여부를 모르므로 stored_id를 채우지 않는다. */
int  db_exec(Db *db, const Statement *st, const ResultSink *sink, int64_t *stored_id, DbError *err);
int  db_state(Db *db);                    /* DB_OK / DB_HALTED_INDEX / DB_HALTED_WRITE */
void db_stats(Db *db, IndexStats *out);   /* /health와 시작 로그용 */
int  db_close(Db *db, DbError *err);
```

- **Parser는 잠금 밖에서 돈다.** 확인 결과 `parser.c`에는 쓰기 가능한 전역 변수가 없다.
- **Executor와 Storage는 잠금을 모른다.** 동시성 정책은 `db.c`에만 둔다.
- **결과 형식은 프런트엔드가 정한다.** CLI는 TSV Sink를, 서버는 예산을 아는 JSON 버퍼 Sink를 넘긴다. `QueryPlan` 구조체는 그대로 JSON 필드가 된다.
- **오류 종류:** `DbError`에 `kind`를 추가한다(`DBE_SQL`, `DBE_STORAGE`, `DBE_INDEX_FAILED`, `DBE_WRITE_FAILED`, `DBE_HALTED`. 서버용 `DBE_LIMIT`·`DBE_NOMEM`은 P3-02에서 추가). CLI는 이 값을 쓰지 않으므로 출력이 바뀌지 않는다.
- **`table_append` 실패 구분:** 지금은 쓰기 오류와 인덱스 등록 실패가 둘 다 -1이다. 이를 "파일을 건드리기 전 실패"(`DBE_STORAGE`), "쓰기 도중 실패"(`DBE_WRITE_FAILED`, 기록 결과 불명), "기록 완료 뒤 인덱스 실패"(`DBE_INDEX_FAILED`)로 나눠 `kind`에 담는다. 마지막 경우에만 기록된 id를 알려 준다. `db_exec`는 뒤의 두 경우에 사유를 남기고 중단 상태로 바꾼다.
- **잠금 구현:** `pthread_mutex`를 쓴다. TDM-GCC 10.3에 winpthreads가 들어 있어서 Windows CLI도 같은 코드로 빌드한다. 동시성 정확성 테스트도 Windows와 Linux에서 모두 돈다. 서버(소켓)만 POSIX 전용이다(D02).

## 지금 코드의 동시성 문제

잠금 없이 여러 스레드가 엔진을 직접 부르면 생기는 문제다. 실제로 나타나는지는 S1x 실험으로 관찰한다. 경쟁은 비결정적이라 실행마다 나타나지 않을 수 있다.

| 위치 | 경쟁 | 결과 |
|---|---|---|
| `Table.fp` 하나를 모두 공유 | A가 `fseek(위치)`한 직후 B가 다른 위치로 옮기고, A는 B의 위치에서 읽는다. **읽기끼리도** 생긴다 | 엉뚱한 줄, "인덱스와 데이터 파일이 일치하지 않습니다" |
| `last_id + 1` (`table_append`) | 두 INSERT가 같은 값을 읽는다 | id 중복 |
| `table_append`의 "파일 끝 위치 → 쓰기" | 두 스레드가 같은 위치를 얻는다 | 트리의 위치가 실제 줄과 어긋남 |
| B+ 트리 분할 중 탐색 | 키를 옮기는 도중에 읽는다 | 잘못된 위치, 잘못된 메모리 접근 |
| 선형 탐색 중 append | 반쯤 쓰인 줄을 읽는다 | 손상 오류 |
| `scan_file`의 `t->last_id = prev_id` | 조회(선형 탐색)가 공유 필드를 쓴다 | INSERT의 id 계산과 경쟁 |

## 읽기 병렬화에서 점검할 공유 상태 (P3-04, DB-P3-D05)

전역 mutex 아래에서는 문제가 없다. rwlock으로 SELECT끼리 동시에 돌리면 **조회 경로에 있는 쓰기**가 모두 경쟁이 된다. 점검 결과는 다음과 같다.

| 조회 경로의 쓰기 | 지금 | 바꿀 내용 |
|---|---|---|
| `scan_file`의 `t->last_id = prev_id` | 시작 시 복원(`table_open`)과 일반 조회(`table_scan`)가 같은 함수를 쓰며, **조회 때마다** 공유 필드를 다시 쓴다 | 두 용도를 나눈다. `table_open`만 마지막 id를 돌려받아 `last_id`를 정하고, `table_scan`은 공유 상태를 쓰지 않는다. **P3-01에서 먼저 한다**(동작 변화 없음, 아래 참고) |
| `fflush(t->fp)` + `fseek(t->fp)` + `getc` | 조회 3곳(`table_find_by_id`, `range_visit`, `scan_file`)이 공유 `FILE*`의 위치와 버퍼를 바꾼다 | `pread(fileno, ...)` 기반 줄 읽기로 바꾼다. 위치는 호출마다 지역 변수로 두고, 읽기 버퍼(64 KiB)는 호출마다 따로 쓴다. 조회는 `FILE*`을 건드리지 않는다 |
| 파일 끝 | 선형 탐색이 EOF까지 읽는다 | `Table`에 `file_size`(INSERT가 배타 잠금 안에서 갱신)를 두고, 조회는 시작할 때의 `file_size`까지만 읽는다. C2의 "시작 시점의 행"이 잠금과 별도로 코드에도 드러난다 |
| `strerror(errno)` | 엔진 오류 메시지 6곳. 반환 버퍼가 스레드 간 안전하다고 보장되지 않는다 | `strerror_r` 기반 도우미 `db_errstr(errnum, buf, n)`. glibc의 GNU판과 XSI판 차이는 도우미 안에 감춘다. 서버 코드(P3-02)도 처음부터 이것을 쓴다 |
| B+ 트리 `bpt_search`·`bpt_range`·`bpt_height`·`bpt_size`·`bpt_mem_stats` | `const BpTree*`이고 쓰기 없음(확인) | 변경 없음. INSERT(분할)는 배타 잠금 안에서만 일어난다 |
| Executor·Parser | 쓰기 가능한 전역 변수 없음(확인) | 변경 없음 |
| `bptree.c`의 `g_fail_after` | 테스트 빌드 전용 전역(메모리 부족 주입) | 동시성 테스트에서는 쓰지 않는다 |

`last_id` 분리는 P3-01에서 먼저 한다. 전역 mutex 아래에서는 경쟁이 아니지만, 조회가 공유 상태를 바꾸는 것 자체가 문제다. 하는 김에 경로를 정리하면 P3-04가 잠금과 `pread`에만 집중할 수 있다. 외부 동작은 같다. 시작 뒤 `last_id`를 바꿀 수 있는 것은 이 서버 자신의 INSERT뿐이기 때문이다.

rwlock의 writer 기아: glibc 기본 rwlock은 읽기를 우선한다. 0.8초짜리 선형 탐색이 계속 들어오면 INSERT가 오래 기다릴 수 있다. P3-04 측정에서 보이면 `PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`를 검토한다.

노드 단위 잠금(latch crabbing)은 하지 않는다. 실제 DBMS는 트리를 내려가며 자식을 잠근 뒤 부모를 놓는다. 우리 트리 연산은 마이크로초 단위이고 병목은 선형 탐색의 파일 읽기라서 효과가 작다. 문서에 설명만 남긴다.

## 서버 아키텍처 (DB-P3-D06, D07, D10)

```text
main: 인자 → db_open(시작 비용 1회) → listen → 워커 N개 생성 → accept 루프
accept 스레드: poll(listen, self-pipe) → accept
               → 큐에 넣기. 가득 차면 비차단 send로 503 BUSY 한 번 → close
워커: 큐에서 fd 꺼내기 → 요청 수신(호출 5초, 전체 10초)
      → 문장 전체 파싱(구문 오류면 400, 0건 실행)
      → 문장마다: 종료 기한 지났나? → 예산 확인 → db_exec(잠금, JSON Sink)
      → 응답 전송(호출 5초, 전체 10초) → close
종료: 신호 → 플래그 + self-pipe → accept 중단
      → 큐의 대기 요청에 503 SHUTTING_DOWN → 처리 중 요청은 계속
      → 유예 10초 뒤: 남은 소켓 shutdown, 워커는 문장 경계에서 멈춤(실행 중 문장은 끝까지) → join → db_close
```

- **큐:** 고리 버퍼 + `pthread_mutex` + `pthread_cond`. accept 스레드는 큐에서 기다리지 않는다.
- **기한 구현:** 소켓을 비차단으로 두고, 매 `recv`·`send` 전에 `poll`에 `min(5초, 전체 기한까지 남은 시간)`을 넘긴다.
- **신호 처리:** 처리기는 `volatile sig_atomic_t` 플래그를 세우고 self-pipe에 1바이트만 쓴다.
- **SIGPIPE:** 무시하고 `EPIPE`를 오류로 처리한다.
- **잠금 밖 입출력:** JSON Sink는 버퍼에만 쓴다. 소켓 쓰기는 잠금을 푼 뒤 한다.
- **문장별 예산:** 문장을 시작하기 전 버퍼 길이를 기억해 둔다. 예산을 넘기면 그 길이로 되돌리고 오류 객체를 붙인다. 오류 객체용 1 KiB는 미리 떼어 둔다.
- **INTERNAL 응답:** 메모리 부족으로 버퍼를 늘리지 못하면 정적 고정 본문으로 500을 보낸다. 이때 앞 결과를 알려 줄 수 없으므로 "결과 불명"이다.
